# Handoff prompt: calibrate another host and replicate E01

Paste the block below into a new coding session on the next machine. It assumes the repository is cloned there and that
the human supplies the sudo password and the approvals out of band. It contains no credentials.

````text
You are working on the VOSS research repo (GitHub: aalhadsawane/voss) on a bare-metal Linux host you can sudo on.
Your job: (A) document this machine completely, (B) run the calibration suites that time each phase of starting a
worker on this machine and on each storage tier it has, (C) replicate experiment E01 (simulator vs real-microVM
emulation) on this machine, (D) commit all raw data and a report on a branch. Do not guess; if something is
ambiguous, ask the human in this session.

Already done on another host (read these first, they are the worked example):
  calibration/specs/i7-12700-64g/SPEC.md          machine spec, generated by tools/calibrate/spec.sh
  docs/validation/i7-12700-64g.md                 calibration results, per-phase tables, interference
  docs/validation/E01-i7-12700-64g.md             E01 replication on that host
  configs/calibration/measured/i7_12700_64g-*/    its bundles
  calibration/raw/i7_12700_64g-*/                 its raw logs
  configs/hardware/I7_64G.yaml, E1.yaml            machine class and E01 worker slice
  configs/e01/i7-12700-64g/                       E01 scenarios for that host
This document is the generic runbook distilled from that session; follow it, substituting this host's label.

## 0. Read first (in this order)
1. AGENTS.md (rules; rule 14: NEVER run reboot or BIOS-dependent suites without explicit human approval in this session).
2. README.md, docs/architecture/10-calibration.md, tools/calibrate/README.md, tools/calibrate/laptop/README.md.
3. docs/validation/E01.md, D-72 in docs/DECISIONS.md, tools/emu/preflight.sh, configs/e01/, configs/hardware/E0.yaml.
4. docs/EXPERIMENT_TODO.md sections X-1 (calibrate several kinds of machine) and X-2 (per-step times for every start
   process). They define the machine specification and per-step breakdown wanted.
5. The worked example for i7-12700-64g listed above.

## 1. Safety and data rules
- Do not format, partition, or write to a raw block device. Benchmarks use files in a scratch directory per storage
  device. Before deleting anything, list it and confirm it is yours (scratch you created). Free space first (df).
- Ask the human before: package installs, any reboot (`appliance` suite), any BIOS toggle (`tme` suite), changing kernel
  parameters, governors or sysctls, enabling services. Record every system change you make and undo it afterwards.
- Never commit secrets, SSH keys, serial numbers, MAC addresses, IPs or the real hostname. Record serials and MACs only as
  a short SHA-256 prefix. Never reuse credentials pasted into any chat.
- Do not lose data: pack each raw result directory as a .tar.zst with a SHA-256 file before any cleanup; keep it outside
  the repo too (state where).
- Quality rules from AGENTS.md apply to any code you change (typed, modules < 400 lines, functions < 50 lines, make check
  passes). If the harness needs a change, make the smallest change in its own PR with a test.
- Values you measure are tagged `measured`; anything copied from literature stays `literature`. Report failures and
  skipped suites honestly with the reason. Do not invent numbers.
- If other users show up in `who`, those may be tmux sessions; ask the human before killing anything. On a shared host,
  ask whether production services may be stopped for quiet timing runs.

## 2. Part A: document the machine (before any measurement)
Choose a short neutral `<host_label>` (CPU family + RAM or disk kind, e.g. `r9-7950x-128g`; never the real hostname) and
state it in the session. Then:
  bash tools/calibrate/spec.sh <host_label> /path/to/scratch/on/tier1 [/path/on/tier2 ...]
This writes calibration/specs/<host_label>/SPEC.md and spec.yaml (read-only probes; serials/MACs hashed; hostname and
home directory replaced). It must report `systemd-detect-virt: none`; if not, stop and tell the human (nested virt is a
different machine class). Add whatever the script cannot see (e.g. TPM firmware version decoding is already handled;
check the output rather than trusting it).

## 3. Part B: calibration suites on every storage tier
1. Install what is missing (ask first):
   apt: python3 fio tpm2-tools openssl cryptsetup qemu-system-x86 e2fsprogs smartmontools numactl cpuid msr-tools
   plus a user-local uv: curl -LsSf https://astral.sh/uv/install.sh | sh && ~/.local/bin/uv sync --python 3.11
2. Build assets:
   mkdir -p ~/voss-calib-work/assets
   sh tools/calibrate/guest/fetch_assets.sh ~/voss-calib-work/assets
   sudo env DOCKER="sudo docker" SUDO="sudo" sh tools/calibrate/guest/build_rootfs.sh ~/voss-calib-work/assets
   (Docker must be running; `sudo systemctl start docker` for this boot only. Do not add --with-ml unless asked.)
3. Make /dev/kvm and the TPM usable without sudo for the whole session (record it as a system change):
   sudo usermod -aG kvm,tss "$USER"
   sudo setfacl -m u:"$USER":rw /dev/kvm /dev/tpm0 /dev/tpmrm0
   Then run VM suites under `sg kvm -c '...'` so the new group applies to this login.
4. Scratch: one directory per distinct storage device/FS configuration, e.g.
   /mnt/nvme1/voss-scratch/ssd, /mnt/hdd1/voss-scratch/hdd. Copy the guest image to each
   (`cp ~/voss-calib-work/assets/voss-guest.ext4 <scratch>/`), and keep the assets on the fastest tier.
5. Preflight: `bash tools/emu/preflight.sh | tee ~/voss-calib-work/preflight.txt`. Check virt=none, /dev/kvm usable,
   TPM 2.0, free space, idle box.
6. Smoke first with `--quick`, then full. Example for a host with one NVMe and one HDD:
   A="--set firecracker=$HOME/voss-calib-work/assets/firecracker
      --set kernel=$HOME/voss-calib-work/assets/vmlinux
      --set rootfs=<nvme>/voss-guest.ext4 --set sebs_rootfs=<nvme>/voss-guest.ext4"
   D="--set ssd_dir=<nvme>/ssd --set hdd_dir=<hdd>/hdd"
   sudo env PATH="$HOME/.local/bin:$PATH" VOSS_NODE=<host_label> python3 -m tools.calibrate.run \
        --suite caps --suite disk --out ~/voss-calib-work/raw $A $D --quick      # needs sudo for dm-crypt/dm-verity
   sg kvm -c 'env PATH=$HOME/.local/bin:$PATH VOSS_NODE=<host_label> python3 -m tools.calibrate.run \
        --suite tpm --suite attest_local --suite tls --suite fc_boot --suite fc_snapshot --suite qemu_vm \
        --suite sebs --out ~/voss-calib-work/raw '"$A $D"' --quick'
   Then the same without `--quick`. `sudo` runs leave root-owned directories: `sudo chown -R "$USER:$USER" <out>`.
7. Distinct labels per storage configuration. `tools/calibrate/common.py::fingerprint` hashes CPU/board/BIOS/RAM only,
   so two disk configurations of one machine would collide. Run one VOSS_NODE per configuration, e.g.
   `<host_label>` (combined, both dirs), `<host_label>_nvme` (ssd_dir only), `<host_label>_hdd` (hdd_dir only). Ingest
   each with `--host <label>`; for an HDD-only configuration also pass `--tier hdd` (D-62) so its only tier fills the
   `ssd` role. Nothing is overwritten; state this in the report.
8. `sebs` interference: run with `--set max_concurrency=<4× hardware threads>`; the suite adds 1,2,4,8, the thread
   count, 2× and 4× automatically and records every level it skips over the 60%-of-RAM budget. Also run two pinned
   variants with `taskset` (children inherit the mask): one thread per physical core, and the SMT siblings of the
   P-cores. Keep pinned runs in a separate raw root (`raw-pinned/`) so they do not enter the bundle fit.
9. Manual suites (rule 14): `tme` needs a BIOS toggle by the human and `--phase on|off`; `appliance` reboots the
   machine N times. **The appliance reboot kills the agent's own session if the agent runs on the measured host.**
   Do all other work, commit and pack first, then arm the bounded reboot loop and hand collection to a follow-up
   session: `bash tools/calibrate/laptop/voss-calib.sh appliance run <N>`, then
   `python3 -m tools.calibrate.run --suite appliance --set step=collect ...`. Report it as armed-not-collected until
   the logs exist (`/var/lib/voss-calib/appliance/probe-*.log`).
10. Ingest:
   uv run python -m tools.calibrate.ingest --raw calibration/raw --host <fingerprint>
   uv run python -m tools.calibrate.ingest --raw calibration/raw --host <fingerprint>_hdd --tier hdd
   Copy the scrubbed raw into the repository: `uv run python -m tools.calibrate.report pack <raw> /tmp/raw.tar.gz`,
   extract, verify no hostname/user strings remain (`grep -rIl <hostname> <dir>`), then copy under `calibration/raw/`.
   Add `calibration/raw/env-<host_label>.txt` (the voss-calib.sh `write_env` format).
11. Add hardware classes: `configs/hardware/<MACHINE>.yaml` (cores, mem_gb, measured ssd/hdd MB/s, tpm, cpu_model) and,
    for E01, a donor slice `<SLICE>.yaml` (e.g. 3 cores / 4 GB per slice). Tag provenance `measured`.

## 4. Part C: replicate E01 on this machine
- Read docs/validation/E01.md and D-72. Emulation: tools/emu (RealtimeKernel + Firecracker backend); scenarios
  configs/e01/{s1_stable,s2_churn,s3_omit_load,s4_load,s3_omit}; seeds 1-3; one run at a time; 10 minutes per run.
- Worker slices: choose so that (slices × slice_ram) leaves the host room for the page cache and (2 slots per slice)
  is close to the hardware-thread count. On the 64 GB / 20-thread i7 the choice was 12 slices of 3 cores / 4 GB.
  Justify it in the report.
- Create `configs/e01/<host_label>/base.yaml` extending `../base.yaml` with this machine's `calibration:` path,
  `scenario.workers` and a host `hw_mix`, plus one file per scenario extending that base.
  **YAML `extends` deep-merges dicts, so `hw_mix` keeps the repository defaults (C0..C3).** Force the host mix on the
  command line: `--set 'scenario.hw_mix={"<SLICE>": 1.0}'`, and say so in the report.
- Pin the emulator and its microVMs to the P-core CPUs (children inherit affinity): the i7 used
  `sg kvm -c 'taskset -c 0-15 ...'` (8 P-cores with SMT). Use this host's P-core mask.
- Simulator side: `uv run voss run <scenario> --out runs-e01-<host_label>/<scenario>-sim-<seed> --set seed=<seed>
  --set 'scenario.hw_mix={"<SLICE>": 1.0}'`.
- Emulation side: `sg kvm -c 'taskset -c <mask> uv run python -m tools.emu.run <scenario> \
  --out runs-e01-<host_label>/<scenario>-emu-<seed> --seed <seed> --assets ~/voss-calib-work/assets \
  --workdir <nvme-scratch>/e01work --set '"'"'scenario.hw_mix={"<SLICE>": 1.0}'"'"''`.
  Run scenarios and seeds sequentially; expect ~11 min per emulation run. Check `emu.json`: `failed` must be `"None"`;
  record `backend` counters (`vm_killed`, `restore_failed`, `restore_without_snapshot`, `claim_without_vm`,
  `boot_retry`, `snapshot_lost`), `kernel_max_lag_s`, affinity and load average.
- `emu.json` contains the real hostname; replace it with `HOST` before committing (`jq '.host="HOST"'`), and do the same
  for any other identifying field. Commit the raw runs: they cannot be reproduced bit for bit.
- Compare: `uv run python -m tools.emu.compare --root runs-e01-<host_label>`. The cut-offs in tools/emu/compare.py are
  fixed in advance; never change them after seeing results. Report per scenario P50/P99 error, KS, success and
  deadline-met differences, level mix, verdict and the emulation counters. Report to
  `docs/validation/E01-<host_label>.md`.

## 5. Deliverables and report
Branch `calib/<host_label>` (never push to main, never force-push), one PR, wait for `make check` green.
Include: spec files and tools/calibrate/spec.sh if not already on main, scrubbed raw data (or checksums + location if too
large, ask), the bundle(s), hardware class YAMLs, E01 configs/runs/report, and any harness changes with tests.
In the final message list: what ran, what was skipped and why, every system change made and how it was undone, where the
data lives (including the out-of-repo archives and their SHA-256), and anything surprising (a suite that failed, a tier
that behaved differently, results far from the simulator). Do not claim a result you have not looked at.
````

## Lessons from the first run (not part of the pasted prompt)

- Run the harness as the invoking user with `sg kvm` for VM suites; running everything under sudo makes `meta.json` carry
  the wrong user and leaves root-owned result directories. `disk` is the only suite that truly needs root.
- `chown -R "$USER:$USER"` after every sudo run, before the next run writes into the same tree.
- The sebs guest image built without PyTorch cannot run `image-recognition`; the suite records a skip. Build with
  `--with-ml` only if that function is required (adds ~10 GB and a long download).
- `qemu_vm` `microvm` boots; `q35` fails with the Firecracker CI kernel (no virtio-pci). Expected on all hosts.
- On a 62 GB host the SUITE's 60%-of-RAM budget allowed 40 guests for 512 MB functions and 20 for 1–2 GB ones; the
  80-guest level was skipped and recorded. Do not lower the budget to force it; report the skip.
- `tools/calibrate/report pack` scrubs user/host names in text files; verify with grep before `git add`.
- The appliance reboot loop is safe (bounded, restores the default target) but it terminates an agent running on that
  host. Pack, commit and push first; collect in a fresh session.
