# E01 on host `i7-12700-64g-asus`: simulator against single-box emulation

**Question.** Does the simulator's end-to-end behaviour match a run of the same scenario with real Firecracker microVMs
on this machine? Design and deviations: D-72; code in `tools/emu/`; scenarios in `configs/e01/i7-12700-64g-asus/`; data in
`runs-e01-i7-12700-64g-asus/` (emulation runs cannot be regenerated bit for bit, so they are committed); tables and CDFs in
`runs-e01-i7-12700-64g-asus/report/`. Machine specification:
[`calibration/specs/i7-12700-64g-asus/SPEC.md`](../../calibration/specs/i7-12700-64g-asus/SPEC.md);
calibration results and per-phase times: [`i7-12700-64g-asus.md`](i7-12700-64g-asus.md).

## Setup

- **Machine.** Bare-metal ASUS PRIME Z790-P WIFI, Intel Core i7-12700 (8 P-cores / 4 E-cores, 20 threads), 62.45 GiB
  DDR5, two Samsung 980 PRO NVMe SSDs in one ext4/LVM filesystem (**no HDD**), Intel PTT TPM 2.0 (firmware
  `600.18.30.2307`), Ubuntu 22.04.5, kernel 5.15.0-198, governor `powersave` (not changed). The emulator and its
  microVMs are pinned to the P-cores and their SMT siblings (`taskset -c 0-15`), the same mask the earlier runs used.
- **Bundle.** `configs/calibration/measured/i7_12700_64g_asus-584bb563fe` (`calibration_hash`
  `e915a94f198db75d73269bf7930907a9ea86f64b479c673489b424a5db96af2a`), measured on this machine with the non-reboot
  suites. The session boot (`reboot_to_kernel`, `appliance_userspace`) keeps its placeholder on both sides.
- **Worker class and count.** 12 donor slices of hardware class `E2` (3 cores, 4 GB, measured NVMe speeds), 2 slots
  each. 16 slices would claim 64 GB of model capacity on a 62.45 GiB machine and leave no room for the page cache that
  snapshots live in; 12 slices model 48 GB and at most 24 concurrent microVMs on the 16 P-core threads, the same
  oversubscription the earlier runs used. Europe only, five functions (dynamic-html, uploader, thumbnailer,
  compression, graph-pagerank), 10 minutes per run.
- **`hw_mix` is forced on the command line.** YAML `extends` deep-merges dicts, so the host file cannot remove the
  repository default classes; every run uses `--set 'scenario.hw_mix={"E2": 1.0}'` and the resolved config is in its
  `manifest.json`.
- **Emulated.** Start-up (boot, snapshot restore, snapshot create), dispatch and function execution run in real
  microVMs. Network, key release, attestation, queueing and the TPM stay models on a wall-clock kernel. Policy code runs
  for real (decision clock `measured`, scale 0); the simulator uses `modeled`.
- **Scenarios.** `s1_stable` (3 inv/s), `s2_churn` (3 inv/s, short sessions), `s4_load` (100 inv/s), `s3_omit_load`
  (100 inv/s, 20% omitting owners), `s3_omit` (3 inv/s, kept for the record).
- **Metrics and cut-offs** are fixed in `tools/emu/compare.py` and were not changed after seeing results: relative error
  of sync P50 and P99, KS distance, success and deadline-met difference, start-level total variation; verdict
  `close` / `partly` / `far`.
- **Seeds.** This replication has **one seed per scenario**, not the three of the earlier hosts. The host is shared: a
  user's DLIO training job (8 processes, ~32 GB) started during the first attempt and pushed load to ~38. The matrix was
  paused, resumed after the owner stopped it, and every emulation run waits for 1-minute load < 3 and > 20 GB free.
  The one-seed matrix fits the quiet window that was available; seeds 2–3 remain open.

**Reading.**

- **Agrees.** The median is within 14–30% in every scenario, the success rate within 0.3 points, the deadline-met
  fraction within 0.7 points, and the mix of start levels (L0-L3: total variation 0.00–0.01). The engine reproduces
  the qualitative behaviour of all five scenarios on this third machine.
- **Does not meet the cut-offs.** The shape of the latency distribution: KS 0.32–0.48, so all five scenarios are
  `partly`, and the two 100 inv/s scenarios are `far` because the emulated tail is pathological. In `s3_omit_load`
  and `s4_load` about 1.9% of successful sync invocations take more than 1 s, 1.4% more than 10 s, and the maximum
  is 29.9 s, against a simulator P99 of 0.2–0.4 s. The slow requests span all start levels (L0-L3), so this is not a
  single cold-start path; it is a real emulation stall that the model does not represent. It did not appear on the
  earlier i7 (emulated P99 0.37–0.88 s over three seeds) and may be a property of this shared host in this run, of
  the snapshot/restore path under the concurrent load, or of the one seed. The committed runs are the evidence; a
  repeat with seeds 2–3 is needed before treating it as a machine effect.
- **`s3_omit`** reproduces `s1_stable` (46/61 ms P50, 140/193 ms P99) because at 3 inv/s one warm worker serves
  everything and the omitting owners never receive work, as on the earlier hosts.
- **Component level.** Absolute differences are milliseconds at the median. As in the earlier reports, the
  invoked `startup` column is not comparable by design (the backend replaces the model's start-up with real work and
  logs it in the events table), and the emulated execution is faster than the modelled `work_ref_s` because the guest
  builds its input locally.

## Emulation counters

Over the five runs: **1,373 VMs killed** by reconciliation (4 and 5 at light load, 13 for `s2_churn`, 594 for
`s4_load`, 757 for `s3_omit_load`), **4 claims without a VM** (booted instead), **4 failed snapshot restores** and
**4 restores for which the model expected a snapshot that did not exist** (both booted instead). `failed` is `"None"`
in every run. The wall-clock kernel's worst delay was **61 ms**; the start/end load averages are in each `emu.json`
(e.g. `s4_load` ended at 1.9/1.6/2.3).

## Limits and bookkeeping

- Single node, 12 workers, **one seed**; hardware class `E2` is a slice of this machine, not a consumer PC. The
  cut-offs are judgements, not statistics. With one seed, a `close`/`partly`/`far` verdict is descriptive, not a
  confidence statement; the earlier 3-seed runs are the comparison for seed noise.
- The host is shared. Resident services (a `cockroach` database, `netdata`, other users' sessions) were present; the
  emulation runs were accepted only when the 1-minute load was below 3 and at least 20 GB was available, and the
  start/end load averages are in every `emu.json`.
- The hard-disk tier is absent on this machine (NVMe-only), so both sides run with the HDD tier off. The session boot
  is the placeholder on both sides until the `appliance` suite is collected.
- `video-processing` and `image-recognition` are excluded (guest input generation and no PyTorch in the image).
- The hostname field in `emu.json` was replaced by `HOST` before committing.
