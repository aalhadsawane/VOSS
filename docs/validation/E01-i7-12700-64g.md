# E01 on host `i7-12700-64g`: simulator against single-box emulation

**Question.** Does the simulator's end-to-end behaviour match a run of the same scenario with real Firecracker microVMs
on this machine? Design and deviations: D-72; code in `tools/emu/`; scenarios in `configs/e01/i7-12700-64g/`; data in
`runs-e01-i7-12700-64g/` (emulation runs cannot be regenerated bit for bit, so they are committed); tables and CDFs in
`runs-e01-i7-12700-64g/report/`. Machine specification: [`calibration/specs/i7-12700-64g/SPEC.md`](../../calibration/specs/i7-12700-64g/SPEC.md);
calibration results and per-phase times: [`i7-12700-64g.md`](i7-12700-64g.md).

## Setup

- **Machine.** Bare-metal MSI PRO Z790-A (MS-7E07), Intel Core i7-12700 (8 P-cores / 4 E-cores, 20 threads), 64 GB
  DDR5-5200, Samsung 980 PRO NVMe, Intel PTT TPM 2.0, Ubuntu 22.04.5, kernel 5.15.0-198, governor `powersave`
  (not changed). Emulator and microVMs pinned to the P-cores and their SMT siblings (`taskset -c 0-15`), the same mask the
  lab-node run used. Runs were sequential; load average stayed below ~3 and the wall-clock kernel's worst lag was 55 ms.
- **Bundle.** `configs/calibration/measured/i7_12700_64g-b4f89a4def` (`calibration_hash`
  `0fc0a683b4ee542160e068a7e9b1d203287eca28f4fab6efee40f3199da0e354`), measured on this machine with the non-reboot
  suites. The session boot (`reboot_to_kernel`, `appliance_userspace`) keeps its placeholder on both sides.
- **Worker class and count.** 12 donor slices of hardware class `E1` (3 cores, 4 GB, measured NVMe/HDD speeds), 2 slots
  each. Rationale: 16 slices (the lab-node count) would claim 64 GB of model capacity on a 64 GB machine and leave no
  room for the page cache that snapshots live in; 12 slices model 48 GB and at most 24 concurrent microVMs on the 16
  P-core threads, the same oversubscription the lab-node run used (32 slots on 20 threads). Europe only, five functions
  (dynamic-html, uploader, thumbnailer, compression, graph-pagerank), 10 minutes per run, seeds 1-3.
  `scenario.hw_mix` is forced to `{E1: 1.0}` on the command line: YAML `extends` deep-merges dicts, so a host file cannot
  remove the repository default classes.
- **Emulated.** Start-up (boot, snapshot restore, snapshot create), dispatch and function execution run in real
  microVMs. Network, key release, attestation, queueing and the TPM stay models on a wall-clock kernel. Policy code runs
  for real (decision clock `measured`, scale 0); the simulator uses `modeled`.
- **Scenarios.** `s1_stable` (3 inv/s), `s2_churn` (3 inv/s, short sessions), `s4_load` (100 inv/s), `s3_omit_load`
  (100 inv/s, 20% omitting owners). `s3_omit` (3 inv/s) is kept for the record: at that load one warm worker serves
  everything, so it reproduces `s1_stable` seed 1 exactly (its omitting owners never receive work).
- **Metrics and cut-offs** were fixed in `tools/emu/compare.py` before the runs and are unchanged: relative error of sync
  P50 and P99, KS distance, success and deadline-met difference, start-level total variation; verdict `close` / `partly` /
  `far`.

**Reading.**

- **Agrees.** The median is within 3-11% in every scenario, success rate within 0.4 points at stable hosts, the mix of
  start levels (L0-L3: total variation ≤ 0.01; 97-99% of successes are L3) and the order of magnitude of every latency
  component. The engine reproduces every scenario's qualitative behaviour on a second, independent machine, and the
  median matches better than on the lab node (-6% to -23% there).
- **Does not meet the cut-offs.** The *shape* of the distribution: KS 0.15-0.26, so four of five scenarios are `partly`
  and only `s2_churn` (KS 0.15) is `close`. The simulator's tail at light load is lighter than the emulation's (-22% to
  -25% P99), consistently across seeds; at 100 inv/s it is mixed (-5% overall, but per seed +96%, -42%, -70% for
  `s3_omit_load` and +72%, -13%, -11% for `s4_load`), so three seeds do not separate a real tail effect from seed noise.
  This is the same failure mode the lab-node report found, but smaller: its light-load P99 error was +270-314%, ours is
  -22-25%.
- **Omitting owners at load.** `s3_omit_load` is the one scenario where success differs materially: 96.7% emulated
  against 99.3% simulated (+2.6 pp). The emulation rejects 3,345 invocations against 712 in the simulator and finishes
  the 30 s drain with 287 async invocations still unfinished against 10; the extra timeouts (441 vs 96) are the
  mechanism. Rejections are admission control under a load the emulated cluster really cannot serve, not lost results.
  Per seed the gap is +0.04, +7.53 and +0.25 pp, so it is dominated by seed 2.
- **Component level.** Absolute differences are milliseconds. The invoked `startup` field is not comparable by design:
  the backend replaces the model's start-up op with real work and logs the real duration in the events table, so the
  simulator's 2 ms warm-start median has no emulated counterpart in that column (emulated start-up is ~0). Real
  start-up from the events table: `emu_boot` median 97-120 ms (spawn + boot + function import + rootfs eviction),
  `emu_restore` median 20-33 ms (spawn + snapshot load + console ping + eviction), `emu_snapshot` median 160 ms at light
  load and 345 ms at 100 inv/s. Emulated execution is ~25-33% faster than the modelled `work_ref_s` at the reference
  input size, because the emulation builds the input in the guest (PREP) and the calibration's work time includes input
  generation for some functions. The `wait` column is ~0 in both sides at the median and only shows up in the tail.
- **What was not checked.** Detection and failover at scale beyond 12 workers and 3 seeds; the hard-disk tier (off in
  both sides); the session boot; any network effect (the network is a model, D-72).

## Emulation counters

Over the 13 emulation runs: **5,522 VMs killed** by reconciliation (session ends, excess warm VMs; 4-25 per light-load
run and 662-1,596 per 100 inv/s run), **13 failed snapshot restores** (each fell back to a boot), **93 restores for which
the model expected a snapshot that did not exist** (booted instead), **17 claims without a VM** (booted instead),
0 boot retries, 0 snapshots lost and 0 executions without a claim. The wall-clock kernel's worst delay was **55 ms**
(median per-event lag below 1 ms). `failed` is `"None"` in every run.

## Limits and bookkeeping

- Single node, 12 workers (not the 16 of the lab-node run), 3 seeds; hardware class `E1` is a slice of this machine, not
  a consumer PC. The cut-offs are judgements, not statistics.
- One run at a time on a shared host: other services (a database, monitoring, a key server) were resident but idle during
  the runs; their load is in the load-average fields of `emu.json`. The hostname field was replaced by `HOST` in the
  committed `emu.json` files.
- `video-processing` and `image-recognition` are excluded (guest input generation and no PyTorch in the image).
- The emulation deep-merges `hw_mix`, so the scenarios' YAML lists E1 but the command line pins `{E1: 1.0}`; the resolved
  config is in every `manifest.json`.
- The appliance session costs are the placeholder on both sides: E01 ran before the reboot suite, and the measured
  session boot (40.5 s power-on → attested) was ingested afterwards into the separate
  `i7_12700_64g_full-b4f89a4def` bundle, so these runs keep their `calibration_hash`. Re-running E01 with `_full` would
  change the modelled session establishment (about 52 s instead of the placeholder) on both sides and is a separate
  experiment.
