# Calibration notes: bare-metal host `i7-12700-64g`

Machine: MSI PRO Z790-A WIFI (MS-7E07), Intel Core i7-12700 (12 cores / 20 threads, Alder Lake), 64 GB DDR5-5200,
4 × 1 TB Samsung 980 PRO NVMe and 4 × 2 TB HGST SATA HDD, Intel PTT firmware TPM 2.0, Ubuntu 22.04.5 LTS, kernel
5.15.0-198. Full specification, exact commands and hashed serials: [`calibration/specs/i7-12700-64g/SPEC.md`](../../calibration/specs/i7-12700-64g/SPEC.md)
(generated by `tools/calibrate/spec.sh i7-12700-64g`).

This is a second calibration machine (X-1). It is **not** node C0 of doc 10 and not the laptop: it is an independent,
real volunteer-class desktop. Two storage configurations are kept as separate labels (below), plus one combined run that
carries both tiers in one raw tree.

**How the per-device labels are kept apart.** `tools/calibrate/common.py::fingerprint` derives the directory name from
`VOSS_NODE` plus a hash of CPU model, board, BIOS and RAM; it deliberately ignores disks, so two storage configurations of
one machine would collide. Each run therefore sets a distinct `VOSS_NODE` (`i7_12700_64g`, `…_nvme`, `…_hdd`), which
`ingest --host` selects and which becomes the bundle directory name. Nothing is overwritten. The combined run is the
canonical bundle used by E01; the two single-device bundles exist so each tier's storage-dependent numbers stand alone
(the HDD one is ingested with `--tier hdd`, D-62). Per-tier data can also be selected inside the combined bundle, because
every `fc_boot`/`fc_snapshot`/`disk` record carries `config.tier`.

## X-2 per-phase breakdown

All values are medians in **milliseconds**, measured on the combined bundle; phases come from the extended probes added
in this branch (`fc_spawn`, `fc_configure`, `fc_start_api`, `fc_boot`, `fc_init_to_done`, `fc_pause`,
`fc_restore_spawn`, `fc_restore_api`, `fc_restore_ack`, `fc_restore`).

### Start a microVM (direct kernel boot, 256 MB guest, fn `boot`)

| Phase | NVMe warm | NVMe cold | HDD warm | HDD cold |
|---|---|---|---|---|
| spawn Firecracker → API socket | 2.4 | 4.5 | 2.4 | 4.6 |
| configure (machine, boot source, drive) | 0.6 | 1.0 | 0.6 | 1.0 |
| `InstanceStart` API call | 7.2 | 11.5 | 7.3 | 11.4 |
| kernel boot → `/voss-init` first line (`fc_boot`) | 46.0 | 62.7 | 46.1 | 89.8 |
| init → guest `done` marker | 3.3 | 6.7 | 3.3 | 15.1 |
| **spawn → done (sum)** | **59.5** | **86.4** | **59.7** | **121.9** |

Boot grows with guest memory (warm NVMe): `fc_boot` 44.6 ms at 128 MB, 46.0 at 256, 48.0 at 512, 53.2 at 1024,
63.6 at 2048 MB. The cold/warm difference is the rootfs read; HDD cold adds ~44 ms over NVMe cold.

### Create a snapshot (pause + full snapshot write)

| Guest memory | Pause | Snapshot create, NVMe | Snapshot create, HDD |
|---|---|---|---|
| 128 MB | 0.2–0.4 | 82.6 | 993.7 |
| 512 MB | 0.2–0.4 | 242.4 | 4,173.1 |
| 2048 MB | 0.2–0.4 | 942.3 | 16,826.7 |

Snapshot size is one full memory file (`fc_snapshot_mb` 128/512/2048 MB), so create time is write bandwidth: ~2 GB/s on
NVMe, ~125 MB/s on the HDD.

### Restore a snapshot (512 MB)

| Phase | NVMe warm | NVMe cold | HDD warm | HDD cold |
|---|---|---|---|---|
| spawn a fresh VMM | 2.4 | 4.5 | 2.4 | 4.5 |
| `/snapshot/load` API | 1.6 | 2.6 | 1.5 | 3.4 |
| resume → guest answers a console ping | 1.3 | 13.7 | 1.3 | 68.6 |
| **load start → answer (`fc_restore`)** | **2.9** | **16.1** | **2.8** | **71.9** |

The cold rows are the page faults of the first response, matching the model's `snapshot_touched` read.

Reading: below the hardware-thread count (≤8) the medians are flat (≤10% growth); above it they roughly double at 20 and
triple at 40 for the CPU-bound functions. Tails grow earlier than medians: at 8 guests p99 is already 1.1–1.3× the
single-guest p99. The very short functions (uploader, dynamic-html) are noise-dominated.

**Skipped levels.** The suite budgets 60% of available RAM per measurement; at 62 GB that allowed 40 guests for the
512 MB functions and 20 for the 1–2 GB ones. Levels skipped, with the reason the suite recorded:

- `dynamic-html`, `uploader`, `thumbnailer`, `compression`, `graph-pagerank`, `graph-mst`, `graph-bfs` at 80: 40,960 MB
- `video-processing` and `dna-visualisation` at 40 and 80: 40,960 / 81,920 MB
- `image-recognition` at every level: the guest image has no PyTorch (`ModuleNotFoundError: torch`)

**Pinning.** `taskset` around the harness (children inherit the mask):

| Run | Mask | Guests | Median, key functions (ms) |
|---|---|---|---|
| one thread per physical core | `0,2,4,6,8,10,12,14,16,17,18,19` | 12 | compression 6.0, thumbnailer 3.9, graph-pagerank 16.4 (single guest: 5.4 / 3.6 / 13.8) |
| SMT siblings of the P-cores | `0-15` | 16 | compression 10.3, thumbnailer 6.0, graph-pagerank 28.2 |

Pinning one thread per physical core (12 guests) costs ≤5% against the 8-guest unpinned medians; using both SMT siblings of
the P-cores (16 guests) costs 1.6–1.8×, close to the 20-guest unpinned level. Both are recorded in
`calibration/raw-pinned/i7_12700_64g-b4f89a4def/` (kept out of `calibration/raw/` so they do not enter the bundle fit).

  1. apt packages installed: `tpm2-tools qemu-system-x86 smartmontools numactl cpuid msr-tools` (plus dependencies). Not
     removed: the harness needs them.
  2. user `voss` added to groups `kvm` and `tss`; ACLs `u:voss:rw` on `/dev/kvm`, `/dev/tpm0`, `/dev/tpmrm0` and
     `u:voss:r` on `/dev/cpu/*/msr`; `msr` module loaded. Needed to open `/dev/kvm` and the TPM without sudo.

  4. No sysctl, governor, kernel parameter or BIOS setting was changed. `kernel.dmesg_restrict=1` was already set.
  5. The scratch directories `/mnt/nvme1/voss-scratch`, `/mnt/hdd1/voss-scratch` and
     `~/voss-calib-work` were created; nothing outside them was written except the assets above and the results in this
     repository.

  skipped (BIOS has TME off, a manual toggle was not approved); `appliance` is armed but not collected.
