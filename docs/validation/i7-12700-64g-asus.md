# Calibration notes: bare-metal host `i7-12700-64g-asus`

Machine: ASUS PRIME Z790-P WIFI, Intel Core i7-12700 (12 cores / 20 threads, Alder Lake), 62.45 GiB DDR5,
two 1 TB Samsung 980 PRO NVMe SSDs in one LVM/ext4 filesystem, **no local HDD**, Intel PTT firmware TPM 2.0
(firmware `600.18.30.2307`), Ubuntu 22.04.5 LTS, kernel 5.15.0-198. Full specification, exact commands and
hashed serials: [`calibration/specs/i7-12700-64g-asus/SPEC.md`](../../calibration/specs/i7-12700-64g-asus/SPEC.md)
(generated by `tools/calibrate/spec.sh i7-12700-64g-asus`). Its E01 replication is
[`E01-i7-12700-64g-asus.md`](E01-i7-12700-64g-asus.md).

This is a third calibration machine (X-1). It is **not** node C0 and not the earlier i7: it is an independent
desktop with the same CPU family but a different board/BIOS, a newer PTT firmware and an **NVMe-only** storage
configuration. The host was shared during the run (other users' `tmux` sessions, a resident `cockroach` database and
`netdata`); their load is recorded below and is part of the measurement, not removed.

## Why this host is a data point

| Dimension | Already covered | This host |
|---|---|---|
| TPM | Intel PTT (0.19 s quote), one laptop TPM (0.51 s) | Intel PTT, **newer firmware** (`600.18.30.2307` vs `600.18.30.2264`); quote 0.214 s |
| Storage | HDD only; NVMe + HDD | **NVMe-only** ext4/LVM (the missing storage class in the coverage table) |
| CPU | 7th-gen mobile; 12th-gen desktop | 12th-gen desktop (same model as `i7-12700-64g`) |
| Memory | 3.9 GB; 64 GB | 64 GB (same class) |
| Firmware/board | two UEFI boards, Secure Boot off | **ASUS PRIME Z790-P WIFI, BIOS 1645**, Secure Boot off |

The fingerprint is **not** a collision: `tools/calibrate/common.py::fingerprint` hashes CPU model, board, BIOS and
RAM, and the board/BIOS differ from `i7-12700-64g` (MSI / A.90). Because there is only one local tier, this host has
one bundle rather than the `_nvme`/`_hdd` split used for the earlier i7 (D-62 does not apply: there is no HDD to
stand in for the SSD role).

rate (same caveat as the earlier i7 note).

## X-2 per-phase breakdown

All values are medians in **milliseconds**, measured on this bundle. Phases come from the same extended probes as
the earlier host (`fc_spawn`, `fc_configure`, `fc_start_api`, `fc_boot`, `fc_init_to_done`, `fc_pause`,
`fc_restore_spawn`, `fc_restore_api`, `fc_restore_ack`, `fc_restore`).

### Start a microVM (direct kernel boot, 256 MB guest, fn `boot`)

| Phase | NVMe warm | NVMe cold |
|---|---|---|
| spawn Firecracker → API socket | 5.4 | 8.3 |
| configure (machine, boot source, drive) | 2.6 | 3.4 |
| `InstanceStart` API call | 19.1 | 22.8 |
| kernel boot → `/voss-init` first line (`fc_boot`) | 60.9 | 66.8 |
| init → guest `done` marker | 3.3 | 7.1 |
| **spawn → done (sum)** | **91.3** | **108.4** |

Boot grows with guest memory (warm NVMe): `fc_boot` 61.0 ms at 128 MB, 60.9 at 256, 63.7 at 512, 68.2 at 1024,
79.9 at 2048 MB (cold: 66.1 / 66.8 / 68.8 / 72.7 / 84.0). The spawn/configure/API phases are 2–3× the earlier i7
(2.4 / 0.6 / 7.2 ms), while the kernel boot is only ~1.3× longer; the sum is ~1.5× the earlier host's 59.5 ms.

### Create a snapshot (pause + full snapshot write)

| Guest memory | Pause | Snapshot create |
|---|---|---|
| 128 MB | ~0.2–0.4 | 120.6 ms |
| 512 MB | ~0.2–0.4 | 792.3 ms |
| 2048 MB | ~0.2–0.4 | 1,522.0 ms |

Snapshot size is one full memory file, so create time is write bandwidth: ~1.6 GB/s at 512 MB and ~1.3 GB/s at
2 GB on this filesystem.

### Restore a snapshot (512 MB)

| Phase | NVMe warm | NVMe cold |
|---|---|---|
| spawn a fresh VMM | 5.3 | 8.2 |
| `/snapshot/load` API | 5.6 | 7.4 |
| resume → guest answers a console ping | 5.9 | 27.8 |
| **load start → answer (`fc_restore`)** | **11.2** | **35.2** |

The cold rows are the page faults of the first response, matching the model's `snapshot_touched` read. The bundle's
`fc_restore` entry uses the load-API probe (`5.6 ms` warm), not the full to-first-response figure.

### Attestation and channels

| Step | Median |
|---|---|
| `tpm2_quote` (PCRs 0–7,10,11) | 213.8 ms |
| `tpm2_checkquote` | 9.1 ms |
| Ed25519 certificate signature (`verify_s` = checkquote + sign) | 14.9 ms |
| end-to-end local attestation (quote + check + sign) | 228.2 ms |
| AK creation (once per boot) | 1,098 ms |
| seal/unseal | 117.4 ms |
| TLS 1.3 handshake (loopback, CPU) | 0.55 ms (CPU 0.68 ms) |
| 1 KiB TLS message overhead over TCP | 0.25 ms |

Reading: below the hardware-thread count (≤8) the medians are flat (≤10% growth, except graph-bfs/mst); above it
they roughly double at 20 and more than double at 40 for the CPU-bound functions. This is the same shape as the
earlier i7, with slightly lower single-guest medians for the long functions.

**Skipped levels.** The suite budgets 60% of available RAM per measurement; at 62 GB that allowed 40 guests for the
512 MB functions and 20 for the 1–2 GB ones. `image-recognition` was skipped at every level because the guest image
has no PyTorch. Levels over the budget are listed in the suite's `records.jsonl`/`meta.json` and are not fitted.

**Pinning.** `taskset` around the harness (children inherit the mask), kept in
`calibration/raw-pinned/i7_12700_64g_asus-584bb563fe/`:

| Run | Mask | Guests | Median, key functions (ms) |
|---|---|---|---|
| one thread per physical core | `0,2,4,6,8,10,12,14,16,17,18,19` | 12 | compression 5.9, thumbnailer 3.9, graph-pagerank 16.7 |
| SMT siblings of the P-cores | `0-15` | 16 | compression 10.3, thumbnailer 5.9, graph-pagerank 29.2 |

Pinning one thread per physical core (12 guests) costs ≤5% against the 8-guest unpinned medians; using both SMT
siblings (16 guests) costs 1.6–1.8×, close to the 20-guest unpinned level. The same crossover as the other i7.

## Limits and bookkeeping

- **One storage tier.** This host has NVMe only, so there is no HDD row and no `_hdd` bundle. Network mounts
  (`/mnt/storage`, `/mnt/beegfs`, `/mnt/shared2`) were deliberately not treated as machine tiers.
- **Shared host.** Other users' `tmux` sessions, a resident `cockroach` database (~14% CPU, ~27% RAM) and `netdata`
  were present throughout; load average was ~0.9–1.3 at the start and is recorded in the run logs. The numbers are
  real measurements of this machine in that state, not a quiet-room calibration.
- **Same CPU family as `i7-12700-64g`.** The new evidence is NVMe-only storage, a different board/BIOS and a newer
  PTT firmware; the CPU-dependent numbers are a replicate, not a new architecture.
- `image-recognition` is unmeasured (no PyTorch image); `q35` QEMU boots fail on the Firecracker kernel; `tme` is
  skipped (BIOS off, no physical toggle); the session-boot entries keep their placeholder until `appliance` is
  collected.
- The numeric canary reports a mismatch on this host (glibc 2.35, Alder Lake), as on the other i7. The simulator's
  results are statistically comparable, not bit-identical, to the published ones (D-70).
