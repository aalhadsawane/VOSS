### What was changed to make the measurements valid

These are the only harness/input changes in this session; every change is committed and, where it affects the harness,
the lock was updated as `570e04bc`/`1de5d147`:

- **`dynamic-html` guest memory 512 → 4,096 MB.** Its largest catalogue input is 100,000 (the handler renders
  10,000,000 random numbers into one Jinja2 page); the 512 MB guest OOM-killed `fnrunner` (exit 137) and lost the whole
  function, because one guest runs all sizes.
- **`dna-visualisation` guest memory 1,024 → 4,096 MB.** Its largest input is 8,000 (8 MB of DNA through squiggle);
  the 1,024 MB guest OOM-killed the guest at that size.
- **`fc_snapshot` create repetitions 10 → 50** (`CREATE_REPS`), matching the contract's `fc_pause`/`fc_snapshot_create`
  n ≥ 50. Restore already used 50.
- **`fn_rss` one sample per function → one per guest at every co-run level**, so every function has n ≥ 10 (the old
  code recorded only the n=1 guest).
- **`snap_size` once → three times per function**, and the scratch directory now falls back from `ssd_dir` to
  `nvme_dir`/`sata_dir`; on an NVMe-only node the old `ssd`-only lookup silently skipped every snapshot size.
- **ML guest image.** `setup`/`node_run.sh ml` builds `voss-guest-ml.ext4` from the same Dockerfile with
  PyTorch 2.4.1 CPU, torchvision 0.19.1 and the ResNet-50 `IMAGENET1K_V1` weights; it is used only by
  `image-recognition`. That function runs one image: 224×224 for sizes 50 and 100, 448×448 for size 400, with a
  2,048 MB guest. Its medians are 0.0749 s, 0.0748 s and 0.2836 s; init 1.46 s; RSS 749 MB; snapshot 2,048 MB.
- **Part C method.** The real mkosi UKI image was not built: Ubuntu 22.04's systemd 249 has no `systemd-repart` and
  mkosi 12 cannot express the `Verity=` repart layout. The handoff allows the host-mode helper, which runs the same
  reboot + TPM round; its image-only steps are reported as missing, not estimated.
- **`spec.sh` prose.** The locked Part A script hard-coded the MSI/4×NVMe/4×HDD summary; `SPEC.md` was re-rendered
  from the probed `spec.yaml` with the existing `spec_md.py` fix (c444ff4). No measurement script was edited for this.

### Cause of the 2026-11-17 shutdown/SSH outage

At **15:30:16** the host-mode driver armed boot 2 (`voss-calib-driver: boot 2 of 10`), set
`default.target → voss-calib.target`, and `systemd-logind` logged `System is rebooting`. The shutdown then stopped
`sshd` (`Stopping OpenBSD Secure Shell server` / `Stopped ...`) but **never completed the reboot**. The persistent
journal ends at 15:30:16; `last` shows runlevel 5 from 15:29:16 until the manual power-cycle at 21:02:13; the journal
has no boot in between. `/sys/fs/pstore` is empty and there is no kernel panic, Oops, BUG, hung-task or watchdog
record. The host was therefore **up but unreachable**, because `sshd` had been stopped as part of the incomplete
shutdown. This is why it looked like an SSH daemon failure.

The probe and the arming logic did not fail: in attempt 1 boot 5's probe had completed, and the first boot of attempt
2 completed; the failure is in the host's shutdown, not in `voss-calib-probe` or `voss-calib-arm`. The likely blocker
is a service/process on this shared host that did not stop (the pfs DLIO SSH sessions, the NFS/BeeGFS mounts, or the
NVIDIA driver). The harness calls `systemctl reboot`; it cannot force a hung shutdown.

**Avoidance for the redo:** stop pfs/other-user workloads and terminate their sessions, stop the background services,
and check `systemctl list-jobs` before arming; run the boots attended/one at a time with console access, not as an
unattended loop on this shared host. The second attempt did stop pfs before the first boot, but pfs reconnected at
15:29:18–15:29:26 and started sessions before the 15:30:16 arm; a watchdog or a login block is needed.

The image-only steps (`boot_firmware`, `boot_loader`, `boot_quote`, `boot_verify`, `boot_first_tls`, `boot_total`,
`image_mem`) remain **missing**, not estimated: they need the dm-verity UKI image. The host-mode values are
`firmware_loader` (firmware + loader), `appliance_attested` (quote + AK creation + checkquote), and
`reboot_to_kernel` (firmware + loader + kernel).

**Data status:** neither attempt is in the new bundle. Attempt 1's raw/logs are archived at
`~/voss-calib-backups/node01-partC-old-20261116/` (SHA-256 raw `99b252a8…`, logs `7e3150ba…`); attempt 2's state is at
`~/voss-calib-backups/node01-partC2-partial-20261117/` (SHA-256 `f06e1975…`). Part C must be redone: 10 complete
boots, no incomplete boot allowed.
