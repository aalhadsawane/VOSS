# 06 · Experiments, Metrics and Validation

## 1. Pipeline

```
configs/experiments/Exx.yaml  ──▶  experiments/runner.py  ──▶  runs/<exp>/<run_hash>/{manifest.json, invocations.parquet,
 (base + sweep grid + seeds)        (multiprocessing,                      events.parquet, samples.parquet, solver.parquet}
                                     one process per run)
runs/…  ──▶  experiments/analysis/*.py (pandas; CI via bootstrap over seeds)  ──▶  figures/Exx_*.pdf + tables/*.csv
```

- An experiment file = `base` config + `sweep:` (cartesian grid over dotted config keys) + `seeds: [..]` (≥ 10 for
  headline results; ≥ 5 for pilots) + `systems:` (list of named configs to compare on the **same scenario hash**).
- Runs are idempotent (skip if `run_hash` exists). Analysis never imports simulator code.
- Each figure is a function `fig_Exx_name(runs_df) -> Figure` registered to its experiment, so any paper figure is
  regenerated by `make figs`.

## 2. Recorded data (`metrics/schema.py`)

| Table | One row per | Key fields |
|---|---|---|
| `invocations` | invocation (final) | ids, fn, origin, cluster, peer(s), slo_class, deadline, **t_arrive, t_response**, outcome, attempts, **components**: `route_s, batch_wait_s, decide_s, queue_s, startup_s(by state), net_in_s, exec_s, net_out_s, retry_s`, `start_state` (S0–S3), wasted_s, replicas, verified, settle_t |
| `events` | state change | peer join/leave/drain/crash, cluster move/split/merge, control failover, spillover, reputation update, ledger epoch |
| `samples` | periodic (e.g., 10 s) | per-cluster size/util/queue/SLO health, donor mem/disk, heartbeat msgs/bytes |
| `solver` | placer call | placer, W, N, K, build_s, solve_wall_s, status, gap, timeout |
| `predictions` | completed invocation (sampled) | predicted dist params vs. realized, for calibration/regret |

All §13 metrics are derived from these tables.

## 5. Statistical protocol

≥ 10 seeds (headline), report mean, std, 95% bootstrap CI, and tails (P50/90/95/99/99.9) per run **then**
aggregate across seeds (never pool-then-percentile without also reporting per-seed). Paired comparisons use the same
scenario hash per seed. Regimes where baselines win are plotted and discussed.

## 6. Validation and calibration plan (spec §9, §7.3)

| Item | Observation source | Model | Check |
|---|---|---|---|
| Cold/warm start per SeBS fn | Firecracker microbench on 2–3 real machines + literature | lifecycle dists | KS / percentile error per function |
| Network RTT/bandwidth | RIPE Atlas / M-Lab summaries (verify) | network model | CDF error |
| Lambda/Azure behavior | Published cold-start/keep-alive numbers (verify) | reference cloud | P50/P99 error |
| Availability | Failure Trace Archive / BOINC studies (verify) | availability generator | Session-length and diurnal fit tests |
| Arrivals | Azure Functions traces (verify) | workload generator | Rate/IAT distribution fit |
| Solver time | Measured on dev machine | `modeled` decision clock | Fit residuals |

Each row is a short entry in `docs/validation/` stating observation → calibration parameter → model → validation
error. The paper's threats-to-validity section draws from these.
