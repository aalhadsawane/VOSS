\section{Detecting Failures and Replacing Schedulers}
\label{sec:ft}

By Property 1, the same mechanisms must handle crashes, churn and malicious owners. This section says how a failure is
noticed, how a failed scheduler is replaced, and how work is recorded.

\subsection{Judging machines by returned work}
A heartbeat is a periodic message in which a machine says it is running. It shows only that the machine can still send
messages. The failures that matter most here keep heartbeats going: a worker that accepts requests and silently discards
them (a \emph{black hole}), a worker that behaves well for hours and then starts dropping work, and an owner who announces
a departure that never happens. We therefore judge a machine by \emph{returned work}: whether work it accepted comes back,
as observed by a party that cannot be faked. Routers run on provider hardware, so their observations are trusted. Workers
and schedulers run attested code, so their observations are honest, although their hosts can still stop or delay them.

Each detector watches for something that must happen if a component works. The router's \emph{dispatch timer} expects the
scheduler to acknowledge a request within 1\,s; if it does not, the router suspects the scheduler. The scheduler's
\emph{result timer} expects a result by the predicted 90th-percentile completion time times 1.2, and at least 3\,s; if none
arrives, it probes the worker and suspects it. Three dispatch timeouts within 5\,s make the router report the cluster as
stalled to the orchestrator. The orchestrator also tracks how long the scheduler takes to place requests, from the
scheduler's signed timestamps, and treats more than 200\,ms as a failure. Finally, the dropped-work estimator and its change
detector (Section~\ref{sec:estimators}) catch workers that drop work selectively or only after a while. Heartbeats remain
as a fast way to notice plain crashes, but a working heartbeat never clears a suspicion. A suspected worker gets no new
work, its unfinished work is duplicated or retried, and it is removed from the plan. A suspected scheduler is replaced.

\subsection{Replacing a scheduler without an agreement protocol}
\label{sec:succession}
The textbook way to replace a failed coordinator is to replicate its state across several machines with a consensus
protocol. Among volunteers that would be slow, and it would bring back an agreement problem among machines that may be
adversarial. \voss{} avoids it for two reasons: the provider's orchestrator is a reliable referee, and a scheduler keeps no
state that cannot be rebuilt. Figure~\ref{fig:failover} shows the sequence.

\textbf{Appointment and epochs.} Each cluster has an \emph{epoch} number in the orchestrator's database. The orchestrator
appoints a scheduler by an atomic compare-and-swap that increments the epoch, much like a lease~\cite{burrows2006chubby}.
The appointment names the cluster, the epoch and the appointee's session certificate. Workers accept assignments only from
the current epoch and the appointed certificate, and answer older epochs with a refusal, so an old scheduler that is still
running is shut out. A scheduler that cannot reach the orchestrator for one lease period (5\,s) also stops on its own. A
cut-off scheduler can therefore cause only duplicate work, which is safe for idempotent functions; for a non-idempotent
function a duplicate sent within the lease period could repeat its effect, and the protocol does not prevent that
(Section~\ref{sec:threats}).

\textbf{Rebuilding the state.} Requests not yet assigned are held by routers, which resend them. Running work and
completed plan actions are held by workers. The estimators' numbers are copied to the provider every 30\,s. Work records are
receipts held by routers. So the new scheduler installs its epoch, asks every worker for its running work, keys and cached
state, restores the estimators from the last copy, and plans again. Because nothing authoritative lives on the old host, a
scheduler machine that restarts is a new instance and must be appointed again.

\textbf{Choosing a successor.} The orchestrator keeps a ranked list of candidates by expected session length, speed,
network position and trust score, spread across cities and providers. Any attested worker can serve, because the scheduler
code is in the image, so promotion needs no boot. A planned handover, for example when the scheduler's owner announces a
departure, first copies the estimators; a false announcement by a malicious owner only causes a clean handover. With the
broker, the successor takes over by subscribing to the cluster's scheduler topic.

\textbf{Worker failures.} When a session ends, its keys and warm sandboxes are lost and its unfinished requests are
retried or duplicated elsewhere, preferably on workers that hold the key. Per-cluster retry limits and spilling to other
clusters prevent retry storms. An owner's notice of departure makes the scheduler stop sending new work to that machine,
but never excuses work that machine dropped.

\subsection{Receipts and credit}
\label{sec:receipts}
Each result carries a receipt signed with the worker's session key. It names the request and attempt, the worker and its
certificate, the epoch, the run time, the amount of work in benchmark units, and a hash of the output. The router checks it
against the certificate and the verifier's revocation list and stores it. A worker cannot claim work it did not do; it can
only decline work, which the detectors above handle.

Receipts pay donors in \emph{credit}, proportional to the benchmark work done rather than elapsed time, so a throttled machine
earns nothing extra. Separately, the provider keeps a long-term \emph{reliability score} per machine: whether its owner kept the
commitments they declared, for example a promised all-night session that ended early. It is used only to reward donors and
to break ties in the planner. It is kept apart from the session-survival and dropped-work estimators, which use other
evidence, so no outcome is counted twice. We do not use a blockchain: a receipt signed by an attested key can already
be checked by anyone, and the remaining risk, the provider deleting records, is better addressed by a signed append-only
log.
