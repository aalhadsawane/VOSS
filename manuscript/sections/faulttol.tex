\section{Detecting Failures and Replacing Schedulers}
\label{sec:ft}
\label{sec:succession}
\label{sec:receipts}

\textbf{Judging workers by returned work.} A heartbeat shows only that a machine can send messages; an owner can keep it
going while discarding the work. We instead check whether work a machine accepted comes back, as seen by a router (provider
hardware) or a scheduler (attested code). The router expects the scheduler to acknowledge an invocation within 1\,s, and
otherwise resends it or tries another cluster and suspects the scheduler. The scheduler expects each result by its predicted
90th-percentile completion time times 1.2, at least 3\,s, and otherwise probes the worker and suspects it. The orchestrator
replaces a scheduler that takes more than 200\,ms per decision. The dropped-work estimator and its change detector
(Section~\ref{sec:estimators}) catch workers that drop work selectively or only after a while. Heartbeats remain as a fast
signal of plain crashes, but never clear a suspicion. A suspected worker gets no new work and is removed from the plan; its
unfinished idempotent work is retried or duplicated elsewhere.

\textbf{Replacing a scheduler without an agreement protocol.} Replicating a scheduler's state among volunteers would need
consensus among machines that may be adversarial. We avoid it because the provider's orchestrator is a reliable referee and
a scheduler holds no state that cannot be rebuilt. Each cluster has an \emph{epoch} number in the orchestrator's database;
the orchestrator appoints a scheduler by an atomic compare-and-swap that increments it, naming the appointee's certificate,
much like a lease~\cite{burrows2006chubby}. Workers accept assignments only for the current epoch and certificate, so a
scheduler that was cut off but is still running is shut out, and a scheduler that cannot reach the orchestrator for 5\,s
stops on its own. The successor rebuilds its view by asking every worker what it is running and holding, restores its
estimators from a copy saved every 30\,s, and plans again; routers resend invocations not yet assigned. A cut-off scheduler
can therefore cause only duplicate work, which is safe for idempotent functions.

\textbf{Receipts.} Each result carries a receipt signed by the worker's session key, naming the invocation, worker, epoch,
run time and work done, which the router checks and stores. A worker cannot claim work it did not do, which is all that
paying donors requires; a blockchain would add nothing, since anyone can check a signed receipt.
