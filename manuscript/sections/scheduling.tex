\section{Scheduling Attested Session State}
\label{sec:sched}

Section~\ref{sec:trust} made trust a resource with a price. This section asks who should hold it, and when. Each cluster (tens of machines) has one scheduler with two jobs: decide which machines hold which attested session state, and assign every invocation to a machine.

\subsection{Why two timescales}
\label{sec:why2}
Could one per-invocation scheduler do both jobs? Three reasons say no.
First, the security cost belongs to a group of machines. A key released to a machine stays for the whole session, so what matters is how many \emph{different} machines hold a tenant's key, and that count does not add up one placement at a time.
Second, robustness is a property of the group: whether demand is still covered if any $f$ machines disappear cannot be read off a single placement.
Third, establishing state takes seconds to tens of seconds (Figure~\ref{fig:cost}), far beyond a per-request budget, so it must happen before demand arrives.
Placement is the opposite: urgent, and a small choice among a few candidates.

So \voss{} uses two loops (Figure~\ref{fig:loops}). The \textbf{slow loop}, the \emph{planner}, runs every 30\,s and whenever things change materially. It decides which machines hold which tenant's key, which snapshots sit on whose disk, how many warm sandboxes each machine keeps, and how many slots are reserved for each tenant.
The \textbf{fast loop}, the \emph{placer}, runs for every invocation and chooses from machines the planner has prepared. The 30\,s period is a design choice, not a measured optimum: plan actions take from a few hundred milliseconds to several seconds, so the period must exceed that, and sessions last minutes to hours, so it must be far shorter. We did not sweep it.

\subsection{What each loop minimises}
\label{sec:objectives}
What we care about in the end is the \emph{SLO violation}: an invocation fails or finishes after its deadline, which for synchronous functions is five times the warm execution time plus 50\,ms. The two loops treat violations differently.

\textbf{The placer minimises each invocation's own risk.} For invocation $i$ on candidate machine $j$ it computes
\begin{equation}
J_{ij}=w_i\,P^{\text{miss}}_{ij}+\varepsilon\,\mathbb{E}[T_{ij}]+\lambda_{\exp}\,x_{ij}.
\label{eq:J}
\end{equation}
$P^{\text{miss}}_{ij}$ is the probability that $i$ violates its SLO on $j$: a machine that fails first counts as a violation, and otherwise the predicted finish time is compared with the remaining deadline. $\mathbb{E}[T_{ij}]$ is the expected latency, and $x_{ij}$ is the exposure added if $j$ does not yet hold the tenant's key.
The default weights give $J$ a plain meaning: one second of expected latency counts like a 5-point rise in violation probability, and giving a medium-sensitivity tenant's key to a new machine of assurance 0.8 costs the same as a 20\% chance of a violation.
We chose per-invocation risk over a P99 target because P99 is a statistic of the whole population and cannot be assigned to one decision, whereas each invocation's own miss probability is the quantity whose average is the miss rate.

\textbf{The planner minimises a surrogate.} At planning time the invocations do not exist, only a forecast of demand. Minimising violations would also be circular, because they depend on the placer's later choices, which depend on the plan. Violations are rare (1--5\%), so an objective built from them is noisy.
And they are not the only cost: warming everything everywhere would minimise violations and hand every tenant's key to every machine. The planner therefore minimises cost \emph{subject to covering demand}. Demand is the number of slots that, assuming Poisson arrivals, covers the forecast load 95\% of the time, so nearly every invocation can start at once, and coverage must hold even after the $f$ largest allocations are lost.
Uncovered demand is charged far more than memory or exposure, so coverage is bought unless the budgets make it impossible, in which case the shortfall is reported. This is a design rationale, not a theorem. Simulated arrivals have bursts that the Poisson model misses, so realised coverage dips during bursts, and the experiments measure the violation rate itself.

\subsection{What the scheduler knows}
\label{sec:info}
For every number a decision uses, a reviewer should be able to tell whether it was observed, learned, forecast or assumed.
\emph{Observed} inputs (busy slots, cached state, provisioned tenants, session expiry, assurance) are reported by workers every 2\,s, plus the scheduler's own dispatches since.
\emph{Learned} inputs (session survival, omission rate, execution time per function and machine) come from online estimators fed only by past outcomes, and \emph{forecasts} (demand over the next 60\,s) are computed from them.
\emph{Calibrated or configured} inputs (start-up and trust costs, network times, host speeds, weights, tenant policy) are fixed before the run and not re-learned.
The scheduler never sees the true end of a session, an invocation's true run time, a host's true behaviour or future arrivals. The code base enforces this by forbidding the policy layer from importing the simulated world.
The speculative part is the last group: the scheduler assumes start-up costs and network times equal their calibrated values and that declared host speeds are exact. A deployment would measure these online. This prototype does not (Section~\ref{sec:threats}).

\subsection{The slow loop: planning keys and warm state}
\label{sec:planner}
Every 30\,s the planner looks at the live, non-draining machines in its view (at most 40), and at the 20 busiest tenants and 50 busiest functions. The long tail stays on the unprovisioned path, which keeps the problem small; the evaluation workload has six tenants and 12 functions, so these caps never bind.
Keys belong to tenants, so the planner first decides which machines hold each hot tenant's key, then which of its functions stay warm there. The result is a \emph{plan} valid for the next 60\,s.

\textbf{Robust coverage.} The planner requires that provisioned, available capacity still covers forecast demand after removing the $f$ largest allocations:
\begin{equation}
\sum_j e_j\,c_{tj} \;-\; (\text{the } f_t \text{ largest } c_{tj}) \;+\; u_t \;\ge\; q_t .
\label{eq:robust}
\end{equation}
Here $c_{tj}$ is the number of slots of machine $j$ reserved for tenant $t$, $e_j$ the estimated chance that $j$ survives the horizon and does not omit, $q_t$ the demand to cover, and $u_t$ the shortfall that is charged.
This is a standard budgeted-robustness constraint~\cite{bertsimas2004price}, written so the integer program stays linear. It needs no model of the adversary, because it assumes the $f_t$ worst machines fail together, even ones with a perfect record. By default $f_t$ is a tenth of the cluster, rounded up, and tenants may opt down.
Allocation also respects each machine's slots, memory and disk, a cap on how much of a tenant's capacity may sit in one failure domain (one network provider or city), the assurance floor, and attestation freshness.

\textbf{Two ways to solve it.} The exact formulation is a mixed-integer program with about a thousand variables per cluster, which we solve with HiGHS~\cite{huangfu2018highs} under a time limit. The \emph{greedy planner} serves hot tenants in decreasing order of demand times cold penalty. For each it repeatedly adds the machine with the best survival-times-assurance per unit of memory and exposure cost, until coverage with the $f_t$ largest removed reaches the demand. It then adds warm sandboxes and snapshots in decreasing order of start-up time saved per megabyte.
Greedy planning takes about \GreedySolveMs\,ms per solve. In a pilot, the exact program needed 0.3--1.1\,s for 10 hosts, 4.7--5.0\,s for 40 and 17--24\,s for 80. Before the experiments we fixed a decision rule: if the exact program improves P99 by less than 5\% over greedy in every regime, greedy is the method and the exact program a reference (Section~\ref{sec:res-plan}).

\textbf{From plan to action.} A plan is re-solved only if the situation changed materially. Otherwise it is compared with its predecessor and turned into idempotent, rate-limited actions sent to workers: prepare (fetch the key and decrypt bundles), pin a snapshot, warm a sandbox, release. Workers confirm completion in heartbeats, and the plan counts only for state they have \emph{confirmed}.

\subsection{The fast loop: placing each invocation}
\label{sec:placer}
For each invocation the placer sees only metadata (function, tenant, remaining deadline, input size, idempotence), the scheduler's current view and the plan. It considers the best $K=12$ machines by a cheap lower bound, from the confirmed provisioned machines and from other attested machines (the \emph{unprovisioned path}, which needs a key release and usually a start-up). Draining, soon-to-expire, low-assurance or memory-short machines are out.
For each candidate it estimates and logs five delays: the wait for a slot, the trust cost (zero if the key is already held), the start-up cost, the network time and the execution time. Completion time is modelled as a shifted log-normal over these parts, and failure probability is the chance that the machine ends its session or omits before the run is over.
A synchronous invocation takes the lowest $J$ immediately. Asynchronous and filler work arrives in 0.2\,s windows and is assigned by minimum-cost matching. All baseline placers use the same candidates and cost model, so differences come from the decision rule alone.

\textbf{Admission, hedging and retries.} If every candidate is almost sure to miss and even the shortest wait exceeds the remaining deadline, the system is overloaded: a synchronous request is rejected and an asynchronous one deferred. Misses caused only by a cold start are admitted, because they warm the caches later requests need.
If the best candidate's miss probability is above 0.2, the function is idempotent and a budget of 10\% of placements allows it, the placer sends a duplicate to the best machine in a \emph{different failure domain} and cancels the loser when the first result arrives~\cite{dean2013tail}.
After a watchdog or failure the invocation is placed again with the failed machine excluded, within a budget. Receipts make duplicates safe for integrity but not for side effects, so hedges and retries apply only to idempotent functions.

\subsection{Estimators}
\label{sec:estimators}
Four small estimators feed both loops, trained online from outcomes the scheduler can see. \emph{Survival} is a Weibull distribution of session length per machine tier, refitted every 60\,s with a time-of-day adjustment. Drain notices can only shorten predicted life, since they may be fake.
\emph{Omission} is a Beta posterior over accepted invocations that return no result, and a change-point test (CUSUM) resets a machine whose behaviour shifts, which defeats owners who behave until they defect.
\emph{Execution time} is a Bayesian regression per function with per-machine offsets~\cite{shafer2008conformal}, and \emph{arrivals} are forecast per tenant and function from counts in 10\,s bins.
Each keeps a few numbers, not a table of past runs, and lives in the scheduler's memory with a checkpoint at the control plane every 30\,s. The planner's robustness does not depend on the omission estimator being right; the estimator only reduces how often robustness has to be used.

\subsection{Clusters and routing}
\label{sec:cluster}
The orchestrator groups workers geographically by clustering on round-trip times, targeting 30 machines per cluster (10 to 60), requires enough failure domains for a robust plan, and rebalances with hysteresis, since a moved worker loses its provisioned state.
A router scores each cluster for an invocation by the delay it expects there, in seconds: the round trip, the cluster's scheduling overhead and backlog, a penalty for a high recent miss rate, the key-release time if the cluster has no capacity provisioned for the tenant, and the cold-start time if it has no warm sandbox. Spilling over to another cluster is thus a decision with an explicit price.
