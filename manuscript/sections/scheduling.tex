\subsection{Why provisioning is separate from request placement}
The scheduler's inputs change at very different rates, and its decisions last for very different times
(Table~\ref{tab:horizons}). How many invocations run on a worker changes every few milliseconds and reaches the scheduler
every 2\,s. A tenant's request rate means something only when averaged over a minute. How long sessions last can only be
learned from many sessions, over hours. On the decision side, assigning an invocation lasts as long as that invocation,
keeping a sandbox warm lasts minutes, and giving a worker a tenant's key lasts the rest of its session.

A decision that outlasts the refresh period of its inputs has to be made from a forecast, ahead of time. A short decision can
react to the latest state. Two more facts separate them. Questions such as ``how many workers hold this tenant's key?'' or
``is demand still covered if any $f$ workers disappear?'' are about a whole set of workers, and a decision about one
invocation at a time cannot answer them. And preparing a worker takes seconds to minutes (Figure~\ref{fig:cost}), more than
an invocation can wait. So the scheduler has two parts. \emph{Provisioning} runs every 30\,s, and earlier if demand or
membership changes sharply: it decides which workers hold which tenant's key, which functions each keeps warm, and how much
concurrency is reserved for each tenant (its \emph{reserved concurrency}). \emph{Request placement} runs for every invocation and picks a worker, usually from those
provisioning prepared. We did not sweep the 30\,s period: plan actions take from a few hundred milliseconds to several seconds,
so the period must be longer, and sessions last minutes to hours, so it must be much shorter.

\subsection{What each part minimises}
Request placement minimises the chance that this invocation misses its deadline. For invocation $i$ and candidate worker
$j$ it computes
\begin{equation}
J_{ij}=P^{\text{miss}}_{ij}+0.05\,\mathbb{E}[T_{ij}]+x_{ij},
\label{eq:J}
\end{equation}
and picks the smallest. $P^{\text{miss}}_{ij}$ is the probability that the invocation fails or finishes after its deadline on
$j$ (the worker may fail first, or the predicted completion may exceed the time left); $\mathbb{E}[T_{ij}]$, in seconds,
separates candidates with similar miss probabilities; and $x_{ij}=\sigma_t(1-a_j)$ is the exposure added if $j$ does not yet
hold the tenant's key, with $\sigma_t$ the tenant's sensitivity and $a_j$ the worker's trust score. With these weights one
second of expected latency counts as much as a 5-point rise in miss probability, and handing a medium-sensitivity tenant's
key to a new worker with trust score 0.8 counts as much as a 20\% chance of a miss. We minimise each invocation's own miss
probability rather than P99 because P99 describes many invocations together and cannot be assigned to one decision.
Asynchronous and background invocations are collected for 0.2\,s and assigned together by a minimum-cost matching.
Invocations that would miss only because of a cold start are admitted because they warm the sandboxes later
invocations need; an invocation is rejected only if every candidate is almost sure to miss.

Provisioning cannot minimise misses directly: the invocations it plans for do not exist yet, and misses depend on later
placement choices, which depend on the plan. It instead keeps enough capacity ready and minimises what that capacity costs.
If a tenant's invocations arrive at random at rate $\lambda_t$ and each runs for $s_t$ seconds on average, the
number running at once is Poisson with mean $\lambda_ts_t$. Provisioning reserves $q_t$ units of concurrency, the 95th percentile of that
number, so that in 95\% of moments an arriving invocation finds reserved concurrency free, and it requires that this survives the loss of
any $f$ workers (by default a tenth of the cluster). With $c_{tj}\le c_j$ the concurrency of worker $j$ reserved for tenant $t$ and $e_j$
the estimated chance that $j$ stays and does not drop work over the next 60\,s,
\begin{equation}
\sum_j e_j\,c_{tj} \;-\; \bigl(\text{sum of the } f \text{ largest } c_{tj}\bigr) \;\ge\; q_t .
\label{eq:robust}
\end{equation}
Removing the largest $f$ contributions is the worst case, so no model of an adversary is needed; Bertsimas and Sim show how
to write this as linear constraints~\cite{bertsimas2004price}. Subject to this, provisioning minimises the memory and disk the
plan uses, key exposure, and the number of new key releases, minus the start-up time that warm sandboxes save. Real arrivals
are burstier than Poisson, so during bursts fewer than 95\% of invocations find reserved concurrency free; the experiments measure the
resulting misses directly.

\subsection{Provisioning algorithms}
Provisioning considers the live, non-leaving workers in its view (at most 40) and at the 20 tenants and 50 functions with the
highest forecast rate; the evaluation workload has six tenants and 12 functions, so these limits never apply. \emph{Greedy
provisioning}, our default, takes tenants in order of how much they lose to cold starts. For each it adds workers one
at a time, choosing the best ratio of reliability times trust score to memory and exposure cost, until
condition~\eqref{eq:robust} holds. On the workers that hold each tenant's key it then adds warm sandboxes and snapshots in
order of start-up time saved per megabyte. It takes about 8\,ms per run. An exact integer program (HiGHS~\cite{huangfu2018highs})
takes about 4\,s per cluster. Before any experiment we fixed a rule: if the exact program lowered P99 by less than 5\% in every
setting, greedy would be the method. The data could not show this, and the exact program was not measurably better
(Section~\ref{sec:res-plan}).

We also derived a provisioning algorithm with more structure. Treat each tenant's reserved concurrency as a loss system: an invocation that finds
all of it in use goes to a worker without the key. The chance of finding all busy depends only on the mean run time and falls
by less with each added unit of reserved concurrency (the Erlang loss formula is convex in that number~\cite{messerli1972}), so the value of a
set of key holders is a monotone submodular function and greedy selection has the classic $(1-1/e)$ guarantee for each
tenant~\cite{nemhauser1978,harshaw2019}, while warm sandboxes can be allocated by marginal gain. The guarantee holds per
tenant only; concurrency shared across tenants, the domain caps and memory limits remove it for the joint plan. We evaluate it as
loss-model provisioning, and it trades latency for exposure rather than replacing greedy (Section~\ref{sec:res-plan}).

A new plan is computed only if its inputs changed beyond a tolerance. The difference to the previous plan becomes actions that
are safe to repeat and rate-limited: fetch the key and decrypt the bundle, keep a snapshot, start a warm sandbox, release.
Workers confirm completed actions in their reports, and placement counts only what they have confirmed.

\subsection{Request placement and what the scheduler knows}
Every number the scheduler uses is reported by a worker (running invocations, cached state, keys held, certificate expiry, trust
score), learned from past outcomes, forecast from learned numbers, or fixed before the run (start-up and trust costs from
the calibration, network delays from distance, declared speeds, weights). It never sees when a session will really end, how
long an invocation will really run, or future arrivals. Placement considers 12 candidates, the workers that hold the tenant's
key and other attested workers that would first need a key release, and excludes workers that are leaving, about to
expire, below the tenant's trust floor or short of memory. For each it adds five predicted delays: waiting for the concurrency limit, getting
the key, starting the function at its current level, moving data over the worker's own link, and running.

The wait for the concurrency limit needs care. A worker's limit is shared by synchronous and asynchronous invocations, and long
asynchronous jobs can use all of it. Estimating the wait from one cluster-wide mean run time would make a queue of
long jobs look short, so synchronous invocations would queue for seconds on the few workers holding a tenant's key rather than
move to another worker. The scheduler therefore replays each worker's queue from the predicted run times of the jobs
it dispatched there, and freed capacity goes to a waiting synchronous invocation before queued asynchronous ones (no
preemption). Every system in our main comparison uses this placement.

If the best candidate's miss probability exceeds 0.2, the function is idempotent and fewer than 10\% of placements have been
duplicated, a second copy goes to the best worker in a different city or provider and the slower copy is cancelled when the
first result arrives~\cite{dean2013tail}. A lost invocation is placed again, excluding the failed worker, within a budget.

\subsection{Estimators}
Four small estimators turn past outcomes into the numbers above; for each we say what it predicts and why we chose it.
\emph{Session survival} is a Weibull distribution of session length per class of machine, fitted by maximum likelihood with
running sessions counted as censored; availability studies find heavy-tailed volunteer sessions~\cite{javadi2013fta}, a
Weibull with shape below one captures that a machine that has been up for an hour is less likely to leave in the next minute,
and two parameters can be fitted from a few dozen sessions. \emph{Dropped work} is a Beta distribution over the chance that an
accepted invocation never returns, updated by two counters, with a prior so that a new worker is not judged on one outcome;
a CUSUM change detector~\cite{page1954cusum} resets it when a worker that behaved starts dropping work.
\emph{Run time} is a Bayesian linear regression of log run time on log input size per function with a small correction per
worker, because run time grows roughly as a power of input size, a prior lets it work from a handful of samples, and Gaussian
processes or regression trees would need more data and time than a millisecond decision allows. \emph{Request rate} is the larger
of two moving averages (1 and 15 minutes), erring towards preparing too much, which costs memory rather than a cold start.

\subsection{Clusters and routing}
In the clustered architecture the orchestrator groups workers by round-trip time into clusters of about 30 (10 to 60) with
enough cities and providers for condition~\eqref{eq:robust} to hold. A router scores each cluster for an invocation by the delay
it expects there: the round trip, the cluster's scheduling time and queue, a penalty for a high recent miss rate, the
key-release time if no worker in it holds the tenant's key, and the cold-start time if it has no warm sandbox.
