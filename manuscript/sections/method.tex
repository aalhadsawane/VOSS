\section{Methodology}
\label{sec:method}

\subsection{What is real and what is modelled}
\label{sec:real}

The scheduler, the run-time model, request placement, failure handling and every compared policy are the code that
would run in a deployment; in the experiments they run inside a deterministic discrete-event simulator. The simulator
models the network, the sessions of workers, and the execution of invocations. Every cost that a volunteer machine
pays comes from measurements of the real image on real machines: boot and attestation, key release, sandbox boot and
snapshot restore per disk type, each function's execution time per input size, and the slowdown of invocations that
run together. Every decision of the scheduler delays the simulation by the time that decision took on a stated
processor (Section~\ref{sec:res-scale}). Two runs with the same configuration and seed produce identical logs, and
each reported run is identified by a hash of its logs.

\subsection{Machines and calibration}

\subsection{Workload, availability and network data}
\label{sec:traces}

\paragraph{Invocations.} Request arrivals come from the Azure Functions trace of 2019~\cite{shahrad2020wild}. For
each of two disjoint sets of days we sample \VAzureFnPerSplit{} functions, stratified by invocation-rate decile, and
replay their per-minute invocation counts as Poisson arrivals within each minute. A function is synchronous if its
trigger in the trace is HTTP. The trace gives no code, so each trace function executes as the measured function whose
execution time is nearest to the trace function's on a logarithmic scale; execution times always come from the
calibration, never from the trace.

\paragraph{Sessions.} Worker availability comes from the SETI@home trace of the Failure Trace
Archive~\cite{javadi2013fta,javadi2009seti}, which records for each host the intervals in which its processor was
available to the project. Each worker replays one host's week. We use two weeks of the trace six months apart,
\VSetiHostsPerSplit{} hosts each. Three limits apply. The trace is from 2007--2009. It records that the processor was
free, which is narrower than the machine being on. The archived copy of the trace that we could retrieve is truncated,
and we use the hosts it contains in full. Table~\ref{tab:traces} compares the interval-length distribution of the
two weeks with the published fit.

\paragraph{Network.} A worker's download rate, upload rate and latency to its ISP are drawn together from the
measurements of fixed broadband in Ookla's open dataset for the first quarter of 2024~\cite{ookla2024}, taken within
\VOoklaRadiusKm{}~km of the worker's city. Workers and clients are distributed over cities in proportion to population
in the United Nations' World Urbanization Prospects~\cite{wup2025}. Delay between cities is the great-circle distance
at the speed of light in fibre multiplied by \VRouteFactor{}, the slope fitted to the median delay between pairs of
servers in a public measurement of pings between cities~\cite{wonderproxy2020}.

\paragraph{Development and held-out data.} The scheduler was developed on one set of trace days and one trace week.
Every result in Section~\ref{sec:results} comes from the other set and the other week, on which each experiment ran
once.

\paragraph{Load.} The trace's functions run for fractions of a second, so the pool as a whole is lightly used at
any load that one run can simulate. \todoitem{T41}{held-out experiments}{Measured share of busy cores in the pool at
each load level.} Load matters at the level of one function: its invocations can run only on its key holders. We
therefore report, for each load level, the load of each function relative to the capacity of its key holders.
\todoitem{T42}{held-out experiments}{Median and 95th percentile over functions of that ratio, per load level and
$K$.}

The primary metric is \emph{deadlines met}: the share of synchronous invocations whose correct result reaches the
client within the deadline. An invocation that is lost and one that is late both count as missed. Latency percentiles
include lost invocations at their deadline. Key holders are reported three ways: concurrent holders, distinct holders
per key version, and key releases per hour. Comparisons between two systems are paired by seed; we report the mean
difference with a 95\% bootstrap interval~\cite{efron1993bootstrap} and correct for the number of stated
comparisons. The comparisons were written down before the held-out experiments ran: at equal $K$, \voss{} against
every provisioning baseline in deadlines met; the holders needed to meet 95\% of deadlines; the failure-handling
policies under owners who drop work; the audit's detection against its bound; and the pool size and load below which
no system meets 95\%.
