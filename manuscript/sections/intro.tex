\section{Introduction}
\label{sec:intro}

Serverless platforms run small pieces of customer code, called \emph{functions}, whenever a request arrives. Most of these
functions finish in well under a second~\cite{shahrad2020wild}, so the useful work is small compared with what surrounds it.
Before a function can run, the platform must create an isolated environment for it and load its language runtime. This
\emph{cold start} can take longer than the function itself. The request must also travel to wherever the function runs.
Providers hide cold starts by keeping environments alive in their datacenters, which holds memory around the
clock~\cite{shahrad2020wild,fuerst2021faascache}. They can do little about distance.

Meanwhile, millions of home and office computers sit close to users and idle for most of the day. Volunteer computing has
used such machines for two decades~\cite{anderson2002seti,anderson2004boinc}, but only for batch jobs with deadlines of
hours. We ask whether volunteer machines can answer requests that must finish in a few seconds.

Two problems stand in the way. The first is \textbf{churn}: an owner can switch off, reboot or reclaim the machine at any
moment, and everything the platform prepared on it disappears, including started environments, cached code and the secret
keys it was given. For a function that runs for tens of milliseconds, preparing this state again costs far more than the
function. The second is \textbf{distrust}: the owner controls the hardware and the operating system, so the owner can read
the customer's code and data, return forged results, or walk away at the worst moment. The two problems feed on each
other. The usual answer to distrust is to check a machine before using it, and that check takes time; churn throws the
result away whenever a session ends.

Earlier work solves parts of this. Volunteer-computing systems run every task on several machines and compare the
answers~\cite{anderson2004boinc}. That multiplies cost, works only for tasks with one right answer, and still shows the
input to every machine that runs it. Serverless schedulers avoid cold starts well~\cite{shahrad2020wild,fuerst2021faascache}
but assume trusted machines that stay up. Confidential-computing designs protect customers from the platform
operator~\cite{arnautov2016scone,wallet2025}, but they run on provider servers and treat the trust check as a one-time setup
step. And the usual way to notice a failed machine, waiting for its periodic ``I am alive'' message (a heartbeat), does not
work against an owner who keeps sending heartbeats while discarding the work. Huang et al.\ call such a failure, where a
component looks healthy to simple checks but fails the requests it serves, a \emph{gray failure}~\cite{huang2017gray}.

\textbf{Our starting point} is that proving which software a machine runs changes what a hostile owner can do. Suppose the
customer's code, and the scheduler's own code, run only inside a locked operating-system image, and a verifier has checked
hardware-signed evidence that the machine booted exactly that image. This check is \emph{remote attestation}. The owner can
then no longer read, forge or change anything inside the image. What the owner keeps is the power switch and the network
cable, so a hostile owner can stop the machine or delay its answers, which is what churn does anyway. The literature calls
these \emph{omission} and \emph{timing} failures~\cite{cristian1991understanding,avizienis2004basic}. A volunteer platform
must tolerate them regardless, so the same mechanisms cover crashes, churn and malicious owners.

This leaves a scheduling problem with a specific shape. During one session a machine goes through three steps for a
customer: it is attested; it receives the customer's decryption key from a key service the customer controls; and it starts
environments for the customer's functions. All three are expensive, since a powered-off laptop needs \CalAttested\,s to
become an attested worker, thousands of times longer than reusing an environment that is already running. All three are
lost when the session ends. And every machine that holds a customer's key is one more place the key could leak from if the
trust assumptions fail. Choosing which machines go through these steps, and when, is a decision with a cost, and it cannot
be made one request at a time.

We present \voss{}, a scheduler built around this problem (Figure~\ref{fig:arch}). A \emph{planner} runs every 30 seconds
and decides which machines hold which customer's key and which functions they keep ready, keeping enough spare capacity
that losing a few machines does not hurt. A per-request step then chooses a machine for each call and sends a duplicate
when the chosen machine is likely to fail. A machine is judged failed when work it accepted does not come back, and a
failed scheduler is replaced by a provider-run coordinator without asking volunteers to agree on anything. Signed receipts
record who did which work. We describe two architectures: one global scheduler on provider hardware, and geographic
clusters whose schedulers run on volunteer machines and are reached through a publish/subscribe broker.

Our contributions are:
(1)~an argument that attestation reduces hostile owners to omission and timing failures, and a statement of the scheduling
problem that remains;
(2)~a two-part scheduler whose planner keeps capacity even if any $f$ machines fail together;
(3)~an architecture for reaching schedulers on volunteer machines whose addresses change and cannot accept incoming
connections, compared with a provider-hosted global scheduler;
(4)~failure detection and scheduler replacement that need no agreement among volunteers;
(5)~a deterministic, calibrated evaluation whose hypotheses and decision rules were fixed before the runs, reported with the
results that went against us.

Planning has the largest effect: it lowers 99th-percentile latency by \GreedyNoneMed--\GreedyNoneHigh\% against provisioning machines only when requests arrive, and judging machines by returned work keeps \VossSuccAlpha\% of requests successful when 20\% of owners drop work, against \HbSuccAlpha\% with heartbeats. Some components did not pay off, including geographic clusters and an exact solver, and a commercial-style datacenter reference is still faster. All results come from simulation and one calibration machine (Section~\ref{sec:threats}).
