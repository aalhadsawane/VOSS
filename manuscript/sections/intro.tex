\section{Introduction}
\label{sec:intro}

\IEEEPARstart{F}{unction-as-a-Service} (FaaS) platforms run short, event-driven functions on demand. In production traces
most functions finish in well under a second \cite{shahrad2020wild}, so their end-to-end latency is set not by computation
but by the \emph{cold start} (creating a sandbox and loading the language runtime) and by network distance to the host
\cite{agache2020firecracker,oakes2018sock,ao2022faasnap}. Providers meet latency targets by keeping sandboxes warm in
datacenters, which pins memory around the clock \cite{shahrad2020wild,fuerst2021faascache}. Meanwhile, consumer desktops and
laptops are numerous, geographically close to users, and idle most of the day. Volunteer computing has harvested such
machines for two decades \cite{anderson2002seti,anderson2004boinc}, but only for batch work whose deadlines are measured in
hours or days.

Serving \emph{latency-sensitive} invocations from volunteer machines raises two problems that batch systems avoid.
\textbf{Churn} is the first. An owner can power off, reboot or reclaim the machine at any moment, and all state the
platform has built on the host (warm sandboxes, cached snapshots, provisioned secrets) disappears with the session. For a
function that runs for tens of milliseconds, rebuilding that state is the dominant cost. \textbf{Distrust} is the
second. The owner controls the hardware and operating system and can read tenant code and data, forge results, or
defect at the worst moment. The two problems interact: the usual defense against distrust is to establish trust in a
host before using it, and churn destroys that trust each time a session ends.

\subsection{Why existing approaches do not solve this}
Each line of prior work handles part of the problem (Section~\ref{sec:related} gives the full comparison).
\emph{Volunteer computing} tolerates untrusted hosts by redundant execution and result voting \cite{anderson2004boinc}, which
multiplies cost by the replication factor, requires deterministic side-effect-free tasks, and cannot hide inputs from the
host. \emph{Serverless schedulers and keep-alive policies} minimize cold starts \cite{shahrad2020wild,fuerst2021faascache}
but assume trusted, always-on servers, so neither churn nor the cost of establishing trust appears in their models.
\emph{Confidential serverless designs} protect tenants from the platform operator with trusted execution environments
\cite{arnautov2016scone,wallet2025} but target provider-managed fleets and treat attestation as a one-time deployment step
rather than a resource with a cost, a lifetime and a security price. \emph{Heartbeat-based failure detection} cannot see a
host that keeps reporting liveness while discarding work, a \emph{gray failure} \cite{huang2017gray} that a malicious owner
can create at will.

\subsection{Our insight and approach}
Our starting point is that attestation changes the fault model. If tenant code and the scheduler's own code run only inside
a measured, owner-locked appliance image whose TPM-backed evidence a verifier checks, then a hostile owner can no longer
read, forge or tamper. What remains is an \emph{omission or timing failure} in the dependability taxonomy
\cite{cristian1991understanding,avizienis2004basic}: the host powers off, drops, delays or throttles. This is the failure
class that churn already forces a volunteer platform to tolerate, so one set of mechanisms covers crashes, churn and
malice \cite{levin2009trinc,veronese2013minbft}.

The reduction exposes the actual scheduling problem. A host is \emph{attested} for the duration of a session, becomes
\emph{provisioned} for a tenant once the tenant's key broker has released a secret to it, and holds \emph{warm} state for a
function once a sandbox or snapshot is ready. This attested session state has three properties that conventional
cluster schedulers do not model: it is \emph{costly to establish} (on our measurements, booting into an attested worker
takes \CalAttested\,s, over three orders of magnitude above restoring a snapshot or resuming a warm sandbox); it is \emph{perishable}, lost at
the end of every session; and it is \emph{exposing}, since each host that holds a tenant's key widens that tenant's attack
surface. Placing an invocation on a host that is not yet provisioned is therefore a priced decision, and so is asking
another host to hold the key.

We present \voss{}, a scheduler for volunteer serverless computing built on this view (Fig.~\ref{fig:arch}). \voss{}
(i) separates \emph{where state lives} from \emph{where an invocation runs} with a two-timescale design: a slow planner
decides which hosts are provisioned and warm for each tenant under a robustness constraint, and a fast placer assigns each
invocation by cost and hedges risky ones; (ii) detects failures from end-to-end \emph{progress} rather than liveness and
replaces failed schedulers with lease and epoch fencing, without consensus among volunteers; and (iii) makes accounting
verifiable through attested receipts instead of a blockchain.

\subsection{Contributions}
\begin{enumerate}
\item \textbf{Problem formulation.} We reduce malicious owners to omission and timing failures through attestation and
formulate volunteer FaaS scheduling as the management of attested session state with explicit establishment cost,
perishability and exposure (Sections~\ref{sec:background}, \ref{sec:trust}).
\item \textbf{Two-timescale scheduling.} A robust provisioning planner with cardinality-constrained coverage plus a
cost-based placer with risk-proportional hedging (Section~\ref{sec:sched}). We find that a greedy planner matches the exact
mixed-integer solution within our pre-set threshold.
\item \textbf{Fault tolerance without volunteer consensus.} Progress-based detection of gray failures, lease and epoch-fenced
scheduler failover on soft state, and attested receipts for accounting (Section~\ref{sec:ft}).
\item \textbf{A calibrated, reproducible evaluation.} A deterministic simulator with parameters measured on a TPM-equipped
machine, an operating-regime analysis that reports where \voss{} and where simple baselines win, and hypothesis tests with
pre-specified decision rules (Sections~\ref{sec:method}, \ref{sec:results}).
\end{enumerate}

\subsection{Summary of findings}
Managing attested session state is the largest lever: planning lowers sync P99 by \GreedyNoneMed--\GreedyNoneHigh\% against no
planning and \GreedyKeepMed--\GreedyKeepHigh\% against keep-alive under medium and high churn. Progress-based detection is
decisive against omitting owners. \voss{} meets a 3\,s sync P99 target in most cells of two regime maps where the strongest
simple baseline never does, but the simple baseline is the only feasible system on confidential-VM substrates at high load.
Several designed components do not pay off: geo-clustering is slower than a single scheduler at our scale, the exact solver
adds at most \MilpGreedyHigh\% over greedy planning, reputation changes P99 by \RepPNinetyninePct\%, and a commercial-style
reference has lower latency. All results are from simulation and a single calibration machine (Section~\ref{sec:threats}).
