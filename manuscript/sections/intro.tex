\section{Introduction}
\label{sec:intro}

Serverless platforms run small pieces of customer code, called \emph{functions}, whenever a request arrives. Most finish in
well under a second~\cite{shahrad2020wild}, so the useful work is small compared with what surrounds it. Before a function
runs, the platform must create an isolated environment for it and load its language runtime. This \emph{cold start} can take
longer than the function, and the request must also travel to wherever the function runs. Providers hide cold starts by keeping
environments alive in their datacenters, which holds memory around the clock~\cite{shahrad2020wild,fuerst2021faascache}.
They can do little about distance. Meanwhile, millions of home and office computers sit close to users and idle for most of the
day. Volunteer computing has used such machines for two decades~\cite{anderson2002seti,anderson2004boinc}, but only for batch
jobs with deadlines of hours. We ask whether they can answer requests that must finish in a few seconds.

Two problems stand in the way. The first is \textbf{churn}: an owner can switch off or reboot at any moment, and everything
prepared on the machine disappears, including started environments, cached code and the secret keys it was given. The second is
\textbf{distrust}: the owner controls the hardware and operating system, so they could read the customer's code and data, return
forged results, or walk away at the worst moment. The two feed on each other. The usual answer to distrust is to check a machine
before using it, and that check takes time; churn throws the result away whenever a session ends. Earlier work solves parts of
this. Volunteer-computing systems run each task on several machines and compare answers, which multiplies cost and exposes the
input~\cite{anderson2004boinc}. Serverless schedulers avoid cold starts well but assume trusted machines that stay
up~\cite{shahrad2020wild,fuerst2021faascache}. Confidential-computing designs protect customers from the platform operator but
run on provider servers~\cite{arnautov2016scone,wallet2025}. And the usual way to notice a failed machine, waiting for its
periodic ``I am running'' message, fails against an owner who keeps sending it while discarding work, a \emph{gray
failure}~\cite{huang2017gray}.

Our starting point is that proving which software a machine runs changes what a hostile owner can do. If the customer's code
and the scheduler's own code run only inside a locked operating-system image, and a verifier has checked hardware-signed evidence
that the machine booted exactly that image (\emph{remote attestation}), the owner can no longer read, forge or change anything
inside it. What the owner keeps is the power switch and the network cable: a hostile owner can stop the machine or delay its
answers, which is what churn does anyway~\cite{cristian1991understanding,avizienis2004basic}. One set of mechanisms then covers
crashes, churn and malice. We use attestation as it is deployed today. Its cost is what matters: a powered-off laptop needs
\CalAttested\,s to become an attested worker, thousands of times longer than reusing a running environment, and the result is lost
when the session ends. That leaves a scheduling problem. A machine goes through three steps for a customer: attested, given the
customer's decryption key, and given started environments for its functions. All are slow, all are lost at the end of a
session, and every machine holding a key is one more place it could leak from. Deciding how many machines to prepare, which, and
when, cannot be done one request at a time.

We present \voss{}, a scheduler built around this problem. A slow \emph{planner}, working from request rates and session lengths averaged over minutes to hours, decides which workers hold
which tenant's key, which functions they keep warm and how many slots are reserved for each tenant, with spare capacity so that
losing a few machines does not hurt. \emph{Request placement} then chooses a worker for each invocation and duplicates
invocations at risk. Workers are judged by whether work they
accepted comes back. We describe two deployments of this scheduler: a single global scheduler on provider hardware, and a
clustered one, in which workers are grouped by geographic proximity and each cluster is scheduled by one of its own volunteer
machines, reached through a publish/subscribe broker. Because a volunteer-hosted scheduler can itself disappear, the clustered
deployment replaces a failed scheduler through a provider-run coordinator, without asking volunteers to agree on anything.

Our contributions are:
(1)~an argument that attestation reduces hostile owners to omission and timing failures, and the scheduling problem that
remains;
(2)~a two-part scheduler, and an analysis of why key placement is a decision about a set of machines, so a slow loop is needed;
(3)~a comparison against the strongest single-loop alternatives we could build, including an Azure-style histogram policy and a
baseline that holds keys ahead on the most reliable machines, with an honest account of where the planner's gain comes from;
(4)~a communication design for schedulers on machines whose addresses change and cannot accept connections;
(5)~failure detection and scheduler replacement without agreement among volunteers; and
(6)~a deterministic, calibrated evaluation whose hypotheses were fixed before the runs.

In simulation the planner lowers 99th-percentile (P99) latency by \RfourDecompGreedyMed\% and \RfourDecompGreedyHigh\% against the best keep-alive policy at medium and high churn, at about 2.5
times the key exposure; most of this comes from deciding how many workers should hold each key, not from choosing which.
Judging workers by returned work keeps \VossSuccAlpha\% of requests successful when 20\% of owners drop work, against \HbSuccAlpha\% with
heartbeats. Several designed components did not pay off, including geographic clusters and an exact solver, and a first version
of request placement handicapped every baseline until we corrected it. All results come from simulation and one calibration
machine (Section~\ref{sec:threats}).
