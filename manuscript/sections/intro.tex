\section{Introduction}
\label{sec:intro}

Serverless platforms run small pieces of customer code, called \emph{functions}, each time a request arrives. Most functions
execute for well under a second~\cite{shahrad2020wild}, and AWS Lambda's default timeout is 3 seconds~\cite{awslambdatimeout}. Before a function can execute, the platform must prepare an isolated
environment for it: start a sandbox (a virtual machine or container that isolates the function), fetch the function's code, load its language runtime and libraries, and run its
initialisation code. This start-up delay, the \emph{cold start}, often exceeds the function's own execution time. Providers avoid
it by starting environments ahead of demand and by keeping each environment alive for a while after a request in case another
arrives (\emph{keep-alive}), which holds memory in their datacenters around the clock~\cite{shahrad2020wild,fuerst2021faascache}.
A request must still travel to the datacenter and back, and keeping environments alive does not shorten that trip. Meanwhile,
millions of home and office computers sit close to users and idle for most of the day. Volunteer computing has used such
machines for two decades~\cite{anderson2002seti,anderson2004boinc}, but only for batch jobs with deadlines of hours. We ask
whether a pool of volunteered machines can serve function invocations that must finish within seconds.

Two problems stand in the way. The first is \textbf{churn}: an owner can switch off or reboot at any moment, and everything
prepared on the machine disappears, including started environments, cached code and the secret keys it was given. The second is
\textbf{distrust}: the owner controls the hardware and operating system, so they could read the customer's code and data, return
forged results, or walk away at the worst moment. The usual answer to distrust is to check a machine before using it, but the
check takes time, and churn throws its result away whenever a session ends. Earlier work solves parts of
this. Volunteer-computing systems run each task on several machines and compare answers, which multiplies cost and exposes the
input~\cite{anderson2004boinc}. Serverless schedulers avoid cold starts well but assume trusted machines that stay
up~\cite{shahrad2020wild,fuerst2021faascache}. Confidential-computing designs protect customers from the platform operator but
run on provider servers~\cite{arnautov2016scone,wallet2025}. And the usual way to detect a failed machine, declaring it
failed when its periodic liveness messages (\emph{heartbeats}) stop, fails against an owner who keeps sending heartbeats while
discarding work, a \emph{gray failure}~\cite{huang2017gray}.

We rely on \emph{remote attestation} to handle distrust. Customer code and our own software run only inside a locked
operating-system image, and before a machine is used, a verifier checks hardware-signed evidence that it booted exactly that
image. The owner can then no longer read, forge or change anything inside it. What the owner keeps is the power switch and the
network cable: they can switch the machine off, or drop or delay its messages, which churn and unreliable networks cause
anyway~\cite{cristian1991understanding,avizienis2004basic}. The mechanisms that handle churn therefore also handle hostile owners.

Before a volunteer machine can run a customer's function, three things must happen, and each takes time. We call a volunteer
machine running our image a \emph{worker}, and a customer a \emph{tenant}. First, the machine must boot our image and pass
attestation. On our calibration laptop (Section~\ref{sec:calib}) this takes \CalAttested\,s from power-on, thousands of times
longer than handing a request to an environment that is already running. \critical{calibration covers one laptop with a hard
disk; extend it to several kinds of volunteer machine, each with its specifications listed.} Second, the worker needs the
tenant's decryption key: tenants encrypt their code, and the saved copies of a started environment's memory and processor state (\emph{snapshots}) made from it, under
their own key, so the provider stores and transfers only ciphertext, and the tenant's key service releases the key only to
attested workers. Third, the worker needs a started environment for the function. Together this takes seconds to minutes, and
all of it is lost when the owner switches off. Every worker holding a key is also one more place the key could leak from; we call the number of key holders, discounted by how well each
is protected, the tenant's \emph{key exposure}. Deciding how many workers to prepare for each tenant, and which ones, is a
decision about a set of workers, and it cannot be made one request at a time.

We present \voss{}, a scheduler for this setting. It separates two decisions. \emph{Provisioning} runs periodically and decides
which workers hold each tenant's key, which of them keep environments for which functions started and idle (\emph{warm}), and how
much capacity is reserved for each tenant, counted as the number of invocations a worker can run at the same time. It works from request rates and session lengths averaged over
minutes to hours, and keeps spare capacity so that losing a few workers does not leave a tenant short. \emph{Request placement}
runs for each invocation: it picks a worker, usually one that provisioning prepared. If that worker is likely to miss the
invocation's deadline, the invocation also runs on a second worker in a different city or internet provider, and the first
result to arrive is used; this is done only for functions that are safe to run twice (\emph{idempotent}). Workers are judged by whether work they accepted comes back, not by heartbeats. We evaluate
two deployments of this scheduler. One is a single global scheduler on provider hardware. The other groups workers into
geographic clusters, each scheduled by one of its own volunteer machines and reached through a publish/subscribe broker; because
such a scheduler can itself disappear, a provider-run coordinator replaces it when it fails, without asking volunteers to agree
on anything.

Our contributions are:
(1)~a scheduler for serverless functions on volunteer machines that separates provisioning, a periodic decision about which set
of workers holds each tenant's key, warm environments and reserved capacity, from request placement, a decision about each
invocation;
(2)~a comparison of provisioning with the keep-alive policies serverless platforms use, including the hybrid histogram policy of
Azure Functions, and with a baseline that gives keys early to the most reliable workers, showing where the gain comes from;
(3)~failure detection that judges workers by returned work rather than by heartbeats;
(4)~a global and a clustered deployment, the latter with schedulers on volunteer machines that are reached through a
publish/subscribe broker and replaced without agreement among volunteers; and
(5)~a deterministic simulator in which every compared system faces the same machine departures and request arrivals, so that
systems are compared on identical conditions and every result can be reproduced exactly.

the best keep-alive policy at medium and high churn, at about 2.5 times the key exposure; most of this comes from deciding how
