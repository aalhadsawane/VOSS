\section{Background and Problem}
\label{sec:background}

\textbf{Terms.} A \emph{tenant} is a customer who deploys functions; an \emph{invocation} is one call of a function. The
\emph{provider} runs the platform, a \emph{volunteer} owns a donated machine, and a \emph{worker} is that machine while it runs
our software. A \emph{sandbox} is a small virtual machine (a microVM) that runs one function in isolation. It is \emph{warm}
when it has started and sits idle, ready for a call; a \emph{snapshot} is a saved copy of a started sandbox that restores
faster than a sandbox boots. Each worker offers a fixed number of \emph{slots}, each running one invocation at a time. A
tenant's \emph{key} decrypts its code and snapshots; only the tenant controls it. We report the 99th percentile of the
latency of synchronous invocations, written P99.

\subsection{Where the time goes}
Before a function runs, the invocation waits for a slot, for the worker to obtain the tenant's key if it lacks it, and
for a sandbox to start. For functions of tens to hundreds of milliseconds, starting the sandbox dominates unless one is
already warm, which is why platforms keep sandboxes alive or restore snapshots~\cite{shahrad2020wild,fuerst2021faascache,ao2022faasnap,cadden2020seuss}.
A function is at one of four levels on a worker: nothing cached (fetch the code, then boot); code on disk (boot); a snapshot
on disk (restore); or a warm sandbox (hand the request over).

Volunteer machines add a cost that datacenters do not have: before running tenant code, a machine must prove which software
it runs, and before decrypting a tenant's code it must receive the tenant's key. Figure~\ref{fig:cost} shows the costs on a
consumer laptop. Handing a request to a warm sandbox takes milliseconds; booting a sandbox takes \CalFcBootWarmMs\,ms with its files in
memory and \CalFcBootColdS\,s from a hard disk; going from power-off to an attested worker takes \CalAttested\,s (median of \CalAttestedN{} boots). Trust costs
thousands of times more than reuse, so it must be prepared before requests arrive. The network adds to this: volunteers sit
on home links with less upload than download, and file systems of 90--450\,MB and snapshots of up to 600\,MB take tens of
seconds to minutes to move. The scheduler charges each candidate worker the transfer time over its own link, workers fetch
from nearby workers before the provider's registry, and snapshots are made locally rather than downloaded.

\subsection{Attestation in brief}
\label{sec:rats}
We use standard remote attestation~\cite{rfc9334}. While a machine boots, a Trusted Platform Module (TPM), the security
chip in most PCs, records a hash of each boot stage; on request it signs these hashes and a fresh random number (a
\emph{quote})~\cite{tcg2019tpm}. A verifier checks the quote against the expected image, and a key service releases a
tenant's key only to machines that pass, as in Keylime~\cite{schear2016keylime} and measured-boot deployments in commodity
operating systems. We use this mechanism as it is; what matters here is its cost (above), that its evidence lasts one boot,
and that it says nothing about whether the machine keeps running.

\subsection{How volunteer machines fail, and the problem}
A worker's \emph{session} lasts from booting our image until the owner switches off. Session lengths are heavy-tailed and
follow the time of day~\cite{javadi2013fta}; sessions end with notice or abruptly, sometimes for a whole city. A machine can
crash, drop a result (an \emph{omission}), or deliver it late (a \emph{timing} failure)~\cite{cristian1991understanding,avizienis2004basic}.
An owner who cannot forge anything can still drop or delay work selectively while the machine keeps sending its periodic
``I am running'' messages, which defeats detectors built on such heartbeats, adaptive ones included~\cite{hayashibara2004phi,huang2017gray}.

Invocations name a tenant and a function, are synchronous (the client waits), asynchronous or background, and carry a
deadline: five times the function's run time on a warm sandbox, plus 50\,ms. Functions are marked idempotent or not; only
idempotent ones are retried or duplicated. This is the contract developers already follow: AWS Lambda retries failed
asynchronous invocations and warns of duplicate events~\cite{awslambdaasync,awslambdaretries}, Google's event-driven
functions run at least once~\cite{gcfretries}, and Azure and Cloudflare deliver events at least once~\cite{azureeventhubsfunctions,cloudflarequeues}.
The scheduler decides which workers receive which tenant's key, which functions they keep warm, and which worker runs each
invocation. The goals are that an owner learns no tenant secret and forges no result; that P99 stays within target despite
churn; that a worker that drops work, or a scheduler that stalls, is bypassed within seconds without trusting its own
reports; and that no worker can claim work it did not do.
