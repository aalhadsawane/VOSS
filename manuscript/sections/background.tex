\section{Background and Problem}
\label{sec:background}

\textbf{Terms.} A \emph{tenant} is a customer of the platform: the developer or company that writes functions. An \emph{invocation} is one call of a function. The \emph{provider} runs the platform, and a \emph{volunteer} or \emph{owner} owns a machine that donates capacity.
A \emph{sandbox} is a small virtual machine (microVM) that runs one function in isolation, and it is \emph{warm} when it is started and idle. A tenant's \emph{secret} is a cryptographic key that only the tenant controls. It decrypts the tenant's code and the saved memory images (snapshots) of its sandboxes, so whoever holds it can read that tenant's code and data.

\subsection{Where the time goes}
The latency of an invocation is a sum of waiting times: choosing a region and a machine, queueing for a slot, making the machine able to run this tenant's code, starting a sandbox, moving data, and running. For functions of tens to hundreds of milliseconds, starting the sandbox dominates unless one is already warm.
Platforms therefore keep sandboxes alive or restore them from snapshots~\cite{shahrad2020wild,fuerst2021faascache,ao2022faasnap,cadden2020seuss}. We distinguish four start-up levels for a function on a machine:
\textbf{L0}, nothing cached; \textbf{L1}, code and file system on local disk (boot and initialise); \textbf{L2}, a snapshot on disk (restore it); \textbf{L3}, an idle warm sandbox in memory (just send the request).
Higher levels cost memory or disk, so choosing which functions to keep at which level where is already a scheduling problem.

Volunteer machines add a term datacenters do not have. Before a machine may run tenant code it must prove what software it runs, and before it may decrypt a tenant's code it must be given that tenant's key.
Figure~\ref{fig:cost} puts these costs on one scale, using a consumer laptop with a TPM, a hardware security chip (Section~\ref{sec:calib}). Resuming a warm sandbox takes milliseconds. Booting a fresh one takes about \CalFcBootWarmMs\,ms if its files are in memory and \CalFcBootColdS\,s if they come from a hard disk.
Getting from power-off to an attested worker takes \CalAttested\,s (median of \CalAttestedN{} boots): \CalReboot\,s for firmware, boot loader and kernel start, and \CalAttestedKernel\,s more until the verifier accepts the machine's proof.
These are upper bounds, because we ran the appliance on a hard disk and in a simplified mode. Even so, trust costs thousands of times more than resuming a sandbox, so \emph{where} it is established cannot be left to the per-request path.

\subsection{Proving what a machine runs}
\label{sec:rats}
We use the vocabulary of the IETF attestation architecture~\cite{rfc9334}. While the machine (the \emph{attester}) boots, each stage (firmware, loader, kernel) is hashed into registers of its TPM, so the final values are a fingerprint of everything that ran~\cite{tcg2019tpm}.
When asked, the TPM signs those values together with a fresh random number from the checker. This signed object is the \emph{quote}. The \emph{verifier} checks the signature, follows the certificate chain back to the chip manufacturer, and compares the fingerprint with known-good values.
A \emph{relying party}, here the tenant's key service, hands over a secret only to a machine with a good result~\cite{schear2016keylime}.
Two facts matter for scheduling: a quote shows what ran at one moment, so evidence goes stale and must be refreshed, and attestation says nothing about availability, since a machine that passes can still stop working.

\subsection{Volunteer machines and how they fail}
A volunteer machine alternates between off and a \emph{session}, an interval in which it is booted into the platform. Session lengths are heavy-tailed and follow the time of day~\cite{javadi2013fta}. A session can end gracefully, with notice, or abruptly, sometimes for a whole city at once.
We classify failures in the standard way~\cite{cristian1991understanding,avizienis2004basic}: a crash stops the machine, an \emph{omission} is a result that never arrives, and a \emph{timing} failure is a result that arrives too late.
Churn produces crashes. An owner who cannot forge anything can still choose \emph{when} to omit or delay, selectively, while the machine keeps reporting that it is healthy. That is the gray failure of Section~\ref{sec:intro}, and it defeats heartbeat detectors, including adaptive ones~\cite{hayashibara2004phi}.

\subsection{The problem}
The input is a stream of invocations, each with a tenant, a function, a service class (synchronous, asynchronous, or low-priority filler), a deadline and an \emph{idempotence} flag. A function is idempotent if calling it twice has the same effect as calling it once.
The platform retries and duplicates only idempotent functions; for the others a lost result is a failure. The machines are a changing population with slots, memory, disk, a location and a session that can end at any time.
The decisions are which machines to attest and provision for which tenants, which functions to keep at which level where, and which machine runs each invocation.
The goals are: \textbf{G1}, a hostile owner learns no tenant secret and forges no result; \textbf{G2}, tail latency stays within target despite churn; \textbf{G3}, a machine that drops work or a scheduler that stalls is bypassed within seconds without trusting liveness signals; \textbf{G4}, a machine cannot claim work it did not do.
We do not defend against physical attacks on the TPM, flaws in the appliance image, side channels, or failure of the provider's own control plane (Section~\ref{sec:threat}).
