\section{Reaching a Scheduler on a Volunteer Machine}
\label{sec:network}

In the clustered architecture each cluster's scheduler runs on one of its volunteer machines. Routers must send it
requests, it must send assignments and plan actions to its workers, and workers must send it their reports. This section
explains why ordinary request--response communication does not work here and what we use instead. In the global
architecture none of this is needed: the scheduler runs on provider hardware at a stable address, and every worker simply
opens a connection to it.

\subsection{The problem: volunteer addresses}
Volunteer machines sit behind home or office routers that perform network address translation. Such a router lets a
machine open connections to the outside, but it drops connections that arrive from outside, because it does not know which
machine inside they are for. The public address of a home connection also changes when the router restarts or the internet
provider reassigns it. A scheduler on a volunteer machine therefore cannot accept incoming connections, and its address
lasts at most one session.

HTTP and gRPC both assume a server that listens at an address its clients know. Here the server would be a home machine
with no way in and an address that changes, and every scheduler replacement would force every router and worker to learn a
new address and reconnect at the same moment. Hole punching, where both sides connect outwards at once, works only for some
pairs of home routers, and the rest need a relay anyway. With hundreds or thousands of clusters, each scheduler changing
machines over time, neither approach scales.

\subsection{Our design: a publish/subscribe broker run by the provider}
\label{sec:broker}
The provider runs a \emph{broker}: a public service at a stable address. Every party opens one long-lived connection to it.
Messages are not addressed to machines; they are published to named \emph{topics}, and the broker delivers each message to
whoever has subscribed to that topic (Figure~\ref{fig:broker}). Each cluster has its own topics, named by the cluster's
number: the scheduler subscribes to the cluster's scheduler topic, each worker to its own topic and to a cluster-wide one,
and routers publish requests to the scheduler topic. Nobody needs another party's address; they only need the cluster
number, which the orchestrator gives them.

We take MQTT~\cite{mqtt5} as the protocol. It was built for devices on unreliable networks, its clients always connect
outwards, and its at-least-once delivery suits our messages: plan actions are safe to repeat, and assignments carry the
scheduler's epoch (Section~\ref{sec:succession}), so a duplicate is recognised. Any broker with topics and outward
connections would serve.

\textbf{Replacing a scheduler becomes simple.} The new scheduler subscribes to the same topic. The topic name does not
change, so no address has to be announced and no worker has to reconnect. Workers only learn the new epoch and the new
scheduler's certificate from the appointment message.

\textbf{The broker cannot forge messages.} MQTT alone does not protect messages from the broker that relays them, and
Buccafurri et al.\ found no earlier proposal that gave end-to-end integrity against an untrusted MQTT broker~\cite{buccafurri2024mqtti}.
We therefore add two layers. Each connection to the broker is mutual TLS with the party's certificate. In addition, every
control message is signed end to end with the sender's session key and carries the epoch and a sequence number; the
receiver checks the signature against the sender's certificate. A worker accepts an assignment only if it is signed by the
scheduler the orchestrator appointed for the current epoch. The broker sees topic names, sizes and timing, and can drop,
delay or reorder messages. These are omission and timing faults, which the detectors of Section~\ref{sec:ft} already handle.
It cannot create, alter or replay a message.

\textbf{Costs.} A message from a worker to its scheduler now travels through the broker, one extra hop; a broker in the
provider region nearest to the cluster keeps it short. The broker is also one more provider service that must stay up, and
production brokers are run as replicated clusters for that reason. The traffic is small: about 0.46\,KB/s per worker in a
scalability pilot, or about 14\,KB/s for a cluster of 30.

\subsection{Why the scheduler is on a volunteer machine at all}
\label{sec:placement}
The clustered design puts the scheduler on a volunteer machine so that the provider runs no server per cluster, and because it is the harder case for fault tolerance, so Section~\ref{sec:ft} tests the mechanisms where they matter.

Compute is not the reason. With the planning times we measured, running every cluster's scheduler on provider hardware
would need about 0.9 processor cores for greedy planning at $10^5$ workers in clusters of 30, and about one core for request
placement at 1\,000 requests per second. Only the exact planner would be expensive, at about 450 cores, and it was not
measurably better (Section~\ref{sec:res-plan}). Hosting on the provider would also remove one round trip from every
synchronous request, remove a malicious scheduler host from the threat model, take the scheduler code out of the image, and
allow larger scheduling domains. Table~\ref{tab:placement} compares the options.

\subsection{What the simulator models}
The simulator models network delay only: each message takes a time derived from the distance between cities, plus 20\,ms
for each end that sits behind a relay (15\% of workers by default), which stands in for the broker hop. It does not model
the broker's capacity, connection set-up, address changes, reconnection, or the cost of signing messages. Sending every
control message through a broker would add the hop for all workers, not 15\%, and we did not sweep this. In E05 the global
scheduler is also hosted on a volunteer machine, so it pays volunteer delays and failures that provider hardware would not;
the comparison is therefore tilted towards the clustered design.
