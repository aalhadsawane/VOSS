\section{Trust and Its Cost}
\label{sec:trust}

The design rests on one claim: attestation turns a hostile owner into an unreliable one. This section states the claim and
its limits, describes how a machine earns a certificate and a tenant's key, and explains why we still limit how many
machines hold each key.

\subsection{Threat model}
\label{sec:threat}
We trust the CPU, its TPM and its memory protection; our measured image; each tenant's own key service; and the provider's
services, to keep running and keep correct records (Table~\ref{tab:threat}). We do not defend against laboratory-grade
physical attacks such as voltage glitching of firmware TPMs~\cite{jacob2023faultpm}, against flaws in our image, against
side channels and traffic analysis, or against failure of the provider's services. An owner who can read the memory of a
running machine, by a cold-boot attack or by probing the memory bus, is also outside the claim below unless the machine
encrypts its memory. Memory encryption (Intel TME, AMD Memory Guard) would close that gap, but consumer firmware ships
with it disabled or absent --- both machines we calibrated report TME off --- and older machines do not offer it at all,
so a volunteer pool cannot be expected to provide it. We therefore treat memory encryption as an optional property of a
trust technology, not as part of the base claim, and report which machines have it.

\textbf{Property 1.} Under these assumptions, everything a worker or scheduler machine does that others can observe, and
that its owner can cause through software, is a crash, a dropped message or a delayed message.
The argument is short. The owner cannot run other software, because it would fail attestation and receive neither a
certificate nor a key. The owner cannot read or change the image's memory or its encrypted disk. Results and receipts are
signed with a key that never leaves the image. What remains is the power switch, the network path, and the choice of when
to stop answering. So the mechanisms that churn forces on us anyway also cover malicious owners, and running every task on
several machines is no longer needed to check results.

Other mechanisms fall short: memory encryption alone attests nothing, voting over several copies triples the cost, and proofs that let a client verify a computation are far too slow for millisecond functions. Confidential virtual machines exist only on server processors, so we treat them as one trust technology among several (Section~\ref{sec:substrates}). A blockchain would protect against no adversary here, because a receipt signed by an attested key can already be checked by anyone (Section~\ref{sec:receipts}).

\subsection{How a machine becomes an attested worker}
The image is a signed kernel with a read-only, integrity-checked root file system, the worker software and the scheduler
code. It has no owner login, and the disk partition that holds the cache is encrypted with a key that the TPM releases only
if the machine booted the expected image. A session starts when the owner reboots into the image and ends on reboot, power
loss, a request to leave, or failure.

Figure~\ref{fig:attest} shows the exchange, which follows Keylime~\cite{schear2016keylime}. The worker creates a fresh
\emph{session key pair} inside the image and includes a hash of the public key in the quote. The verifier checks the quote,
the certificate chain and the boot record. It also acts as the certificate authority: if everything matches, it issues a
\emph{session certificate} that names the machine, carries the session public key and a trust score, and expires when the
session expires. Periodic re-quotes keep it valid during the session. When the session ends, or a re-quote fails, the
verifier revokes the certificate and tells the routers, the scheduler and the key services.
Every connection in the system is mutual TLS with this certificate, so both ends of every connection are either a provider
service or an attested image. Two consequences matter for scheduling. Trust is \emph{perishable}: it lasts one session at
most. And identity costs hardware: a worker is identified by a hash of its TPM's endorsement key, so creating many
identities requires many machines~\cite{douceur2002sybil}.

\subsection{How a worker gets a tenant's key}
\label{sec:provisioning}
Attestation shows that a machine runs our image, not that it may see a particular tenant's data. Each tenant's key service
applies the tenant's policy, for example ``accept image versions at or above this one''. Giving worker $j$ tenant $t$'s key
takes one round trip: the worker presents its certificate over mutual TLS, the key service checks the policy and returns
the key encrypted to the worker's session public key, and the worker keeps it in memory only. We say the worker is then
\emph{provisioned} for the tenant. Because bundles and snapshots are encrypted at rest (Section~\ref{sec:atrest}), any worker
may store and forward them, but only provisioned workers can use them. Snapshots contain the decrypted memory of a running
sandbox, so only provisioned workers create them, and they are encrypted with the tenant's key before being written.

Which party the tenant must trust for confidentiality depends on its policy. If the key service accepts any certificate the
verifier issued for an approved image, the tenant trusts the verifier as well. If the policy requires a fresh quote, the key
service checks the quote itself and does not depend on the verifier, at the cost of one more quote per release. The
simulator charges a fixed, measured cost for the policy check.

\subsection{Key exposure, and why we limit it}
\label{sec:exposure}
Every machine that holds a tenant's key is one more place the key could leak from if our assumptions fail. We measure this
as the tenant's \emph{key exposure},
\begin{equation}
E_t = \sum_{j \text{ holds } t\text{'s key}} (1-a_j),
\label{eq:exposure}
\end{equation}
where $a_j \in [0,1]$ is machine $j$'s \emph{trust score}: a value set by policy for its trust technology (0.8 for the TPM
image on consumer hardware, 0.95 for a confidential virtual machine), reduced if its firmware is not on a known-good list.
Exposure is a count of key holders, each discounted by how well protected it is. It is not a probability of compromise,
and we report it next to latency rather than folding it into one number. Tenants choose how much exposure matters to them,
and can set a minimum trust score below which a machine never gets their key.

If attested machines are honest, why limit exposure at all? Three reasons. First, honesty holds only under the assumptions
above, and on consumer hardware the assumptions we exclude are the realistic ones: reading the memory of a running machine
that does not encrypt memory, flaws in TPM firmware~\cite{jacob2023faultpm}, and bugs in our image. Limiting exposure is the
defence for the case where attestation is not enough. Second, the two possible failures are not alike. A forged result
harms one invocation and can be caught by re-running it. A leaked key is silent and permanent: it decrypts every bundle and
snapshot of that tenant, past and future, wherever the ciphertext is stored, and reading memory passively is the easiest
physical attack. Third, it costs almost nothing. Removing the exposure term from \voss{} changes 99th-percentile latency by
\AblExposureP\,s (95\% interval up to \AblExposurePHi\,s, including zero) while raising exposure by \AblExposureExp{}
(Section~\ref{sec:res-plan}). Dropping it would weaken the defence without making anything faster.

\subsection{Trust technologies}
\label{sec:substrates}
The scheduler does not depend on how a machine establishes trust. For each \emph{trust technology} a data file tells the
simulator how long attestation takes, how long it lasts, what each start-up level costs and what trust score the machine
carries. We model five: the TPM-attested image on consumer hardware, with costs we measured (Section~\ref{sec:calib}); two
kinds of confidential virtual machine on server processors, with costs from the
literature~\cite{amd2020snp,misono2025cvm,holmes2024severifast,li2023bifrost}; a measured hypervisor started under the
owner's operating system; and no attestation, which the baselines use.
