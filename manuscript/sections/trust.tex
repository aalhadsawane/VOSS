\section{Trust Model and Establishment}
\label{sec:trust}

This section states the threat model, shows how attestation reduces malicious owners to omission and timing failures,
and defines the three pieces of attested session state that the scheduler manages: the attested session, tenant key provisioning,
and the exposure they create.

Table~\ref{tab:threat} summarizes the adversaries. We trust the CPU, its TPM and memory encryption; the measured appliance image
(kernel, monitor, agent, scheduler code); each tenant's own key broker; and the provider-operated control plane, for
availability and accounting only. Out of scope are laboratory-grade physical attacks such as voltage glitching of
firmware TPMs \cite{jacob2023faultpm}, vulnerabilities in the appliance itself, side channels and traffic analysis, and attacks on or
failure of the control plane.

\textbf{Property 1 (threat reduction).} Under these assumptions, every behavior of a worker or scheduler host that other
components can observe is a crash, an omission or a delay. The argument is that the owner can neither run code other than the measured
image (it would fail attestation, so no session certificate or tenant key is issued) nor read or modify the image's memory or its sealed
state, and that results and receipts are signed with a key that never leaves the appliance. The owner retains only what lies outside the attested
stack: power, the network path, and the timing of when to stop answering. The consequence we use throughout is that the fault tolerance
mechanisms needed for churn already cover malice (Section~\ref{sec:ft}), and that redundancy is no longer required for
integrity.

\textbf{Why not other mechanisms.} Memory encryption alone is not a trusted execution environment: the operating system still sees
plaintext and nothing is attested. Replicated execution with voting triples cost and presumes comparable outputs. Zero-knowledge
or other verifiable computation is orders of magnitude too slow for functions of milliseconds. Server confidential VMs have the strongest
isolation but exist only on server CPUs; we model them as a substrate (Section~\ref{sec:substrates}). A blockchain ledger would protect against no
adversary in this model, because receipts signed by an attested key are already third-party verifiable and the only residual risk, a
trusted control plane deleting records, is better met by a signed transparency log (future work).

\subsection{Attested appliance and session}
The appliance is a unified kernel image signed for Secure Boot with a read-only integrity-protected root (dm-verity), Firecracker, the
worker agent and the scheduler code, with no owner login, kernel lockdown, IOMMU and integrity measurement (IMA) enabled. The data
partition holding the caches is encrypted with a key sealed to the expected PCR values. A session begins when the owner chooses to
donate and reboots into the image, and it ends on owner reboot or power loss (abrupt), on an owner drain request with a deadline
(graceful), or on failure.

Fig.~\ref{fig:attest} shows the attestation protocol, which follows Keylime-style remote attestation \cite{schear2016keylime} in RATS
roles (Section~\ref{sec:rats}). The agent generates a \emph{session key pair} inside the appliance and binds its public half
into the quote, as the hash of the key appended to the verifier's nonce. The verifier checks the quote signature and the endorsement-key
certificate chain, replays the event log against reference values for the measured image, and, if the result is acceptable, issues a
\emph{session certificate} carrying the host identity, session public key, an assurance score and an expiry. Every channel of the system
(to routers, the scheduler, the KBS, and peers) is TLS with this certificate, so there is no untrusted operating system on any path. Two
properties are decisive for scheduling. \emph{Trust is perishable}: the certificate expires at the earlier of session end and
the last successful quote plus a validity period, is extended by periodic re-quotes, and is revoked on a failed re-quote, upon which the verifier
notifies routers and the scheduler. And \emph{identity costs a machine}: a worker's identity is the hash of its TPM endorsement key, so creating identities
costs hardware \cite{douceur2002sybil}.

\subsection{Tenant key provisioning}
\label{sec:provisioning}
Attestation proves that a host runs the appliance, not that it may see a given tenant's data. A tenant's KBS holds a policy (for
instance, accept certificates for appliance measurements at or above a version, optionally with a fresh quote). Making worker $j$
\emph{provisioned} for tenant $t$ (the flag $K[t,j]=1$) takes one round trip: the worker sends the KBS its certificate, the KBS checks the policy and returns the key
wrapped to the session public key, and the worker keeps it in memory only. This round trip, plus decrypting the tenant's bundles, is the
$T_{\text{prov}}$ term of Eq.~\eqref{eq:latency}. Tenant code bundles in the registry and peer caches are encrypted with the tenant key, so any
worker may store and forward ciphertext but only provisioned workers can use it. Snapshots contain decrypted memory, so they are written
only by provisioned workers, shared only with provisioned workers of the same snapshot class (CPU model, kernel, monitor version), and counted in
exposure.

\subsection{Exposure and assurance}
\label{sec:exposure}
Every provisioned host is a place from which a tenant's secret could leak if the trust assumptions fail. We define the \emph{key exposure}
of tenant $t$ as
\begin{equation}
E_t = \sum_{j\in \mathrm{KH}(t)} (1-a_j),
\label{eq:exposure}
\end{equation}
where $\mathrm{KH}(t)$ is the set of hosts holding $t$'s key or decrypted artifacts and $a_j\in[0,1]$ is the host's \emph{assurance}:
the product of a base value for its trust substrate and a firmware-policy factor (known-good versus trust-on-first-use), fixed when the verifier issues
the session certificate. Staleness is not a continuous factor: a certificate simply expires, and a host whose quote would expire within the planning horizon is excluded from plans. The scheduler weights exposure by a tenant sensitivity $\sigma_t$ and
enforces an assurance floor for sensitive tenants. Exposure is a transparent proxy for attack surface, not a probability of compromise,
and base assurances are policy parameters, not measured truths; we therefore report latency, exposure and robustness as a Pareto
front and never as one weighted number.

\textbf{Inputs, outputs and constraints.} \emph{Attestation} takes a TPM quote over the appliance's measured boot (event log, PCR values), the endorsement-key certificate chain and a fresh verifier nonce, and outputs a session certificate with assurance $a_j$ and an expiry, or a rejection. It is constrained by reference measurements known to the verifier, the certificate validity period and re-quote interval, and the TPM's quote rate.
\emph{Provisioning} takes the certificate and the tenant's KBS policy and outputs the wrapped key or a denial. In the simulator both are sequences of simulated delays: network round trips through the geographic model, a TPM quote and verification service time from the substrate profile, and a fixed policy-check cost. The tenant key never reaches the scheduler or the orchestrator: the scheduler learns only that $K[t,j]=1$, from the worker's heartbeat.

\subsection{Substrate profiles}
\label{sec:substrates}
\voss{} separates the scheduler from the mechanism by which a host establishes trust. A \emph{substrate profile} is data that tells one generic lifecycle
engine how a worker establishes trust, how long it lasts, what the start-up tiers cost, what assurance the host carries, and how execution is slowed. We
model five (Table~\ref{tab:substrates}). The primary, \texttt{appliance\_tpm}, is the TPM-attested appliance on consumer hardware, whose costs we measured
(Section~\ref{sec:calib}). The server confidential-VM classes (\texttt{cvm\_snp}, \texttt{coco\_pool}) use ranges from the
literature \cite{amd2020snp,misono2025cvm,holmes2024severifast,li2023bifrost}, \texttt{drtm\_hv} models a measured hypervisor launched under the
owner's operating system, and \texttt{none} is the unattested reference used for baselines.
